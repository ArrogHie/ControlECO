# 自动记账逐应用解析规则

初次核对基线：2026-11-02，版本 1.0.5（40）；支付宝通知与页面规则于 2026-11-05 更新。本文说明“原文／页面节点如何变成交易候选”，供定位漏识别、金额错误和补充规则使用。采集权限、同笔合并、入账及 ASK 处理见[自动记账捕获机制](自动记账捕获机制.md)，修改步骤见[维护指南](通知规则维护指南.md)。**生成候选不等于新增账单**，还会经过合并、终态和入账流程。

示例分两类：**真机来源回归**指仓库测试明确注明来源于实际捕获记录，可能经过脱敏整理；**普通回归**指已有可执行测试，但不能据此声称对应 App／机型已真机验证。本文引用的测试已重新执行，结果见末节；没有测试样本的规则明确标出缺口。

## 2. 共同的提取方法

### 2.1 支付／电商通知

入口为 `NotificationRules.parse(packageName, title, text, bigText, postTime)`。来源校验和文本归一化后，先尝试第 4 节的支付宝支出积分专用规则；未命中时使用以下通用流程：

1. 包名必须在支付三包或电商包名表；拼接非空标题、正文和长正文。
2. `normalize` 转换全角数字、`￥`、全角小数点，去掉 `[11条]` 等折叠计数，合并空白；保留中文逗号、句号作为金额匹配边界。
3. `maskCardTails` 遮罩“尾号1234”“储蓄卡(1234)”等尾号；微信另须标题或正文包含“微信支付”。
4. 噪声词在**缺少交易确认短语**时才否决；例如验证码、额度、物流、领券。随后排除明确红包领取／到账通知；此红包过滤实际用于本引擎所有来源。
5. 电商／外卖额外要求确认短语，如“支付成功／已支付／交易成功／扣款成功／收款成功／退款成功／自动扣款”。这只是短语匹配，没有另做完整的通知状态机。
6. 判方向：含“退款／退回”优先为退款收入；其次“向你付款／付款给你／转账给你／向你转账／收到一笔”为收入；再比较普通收入词与支出词。两边都中或都不中则放弃。
7. 取金额，调用 `Money.parseCents` 转为分；要求 `0 < amountCents <= 1_000_000_000`（1000 万元）。

普通收入词为“收款／到账／入账／收入”；非微信支出词为“已支付／支付成功／支出／消费／付款／扣款／扣费／支付凭证”。微信支出只认“已支付／已扣费／自动扣费”。

| 金额优先级 | 方法 | 例子与边界 |
| --- | --- | --- |
| 1 | 反向表达式：金额在动词前 | `0.01元的支出`；允许最多 8 个非中文逗号、句号、数字的修饰字符，支持千分位；微信使用独立动词表 |
| 2 | 方向对应正向表达式 | `收款2.00元`、`消费50.00元`；关键词与金额间最多 8 个非数字／货币符号／小数点字符，数字后须有“元” |
| 3 | 货币符号兜底 | 方向已成立时取首个 `¥金额`，如 `已支付¥12.80`；不代表已理解整段文案中所有金额 |

退款、收入、支出各有正向式；微信的支出正向式和反向式同时收窄，避免“已支付¥12.80，满620元消费立减”反而取到 620 元。不要只改方向词、不改金额式。

`parse` 返回空时，还有独立处理：普通明确方向且无金额可由 `parseDirectionOnly` 进入补金额流程；折叠摘要、红包及退款不走该补录入口。支付三包的无金额退款由独立提醒识别路径保存金额 0 的退款待处理条目；0 代表金额未知，不是已入账的 0 元收入。分组摘要补全由 `GroupNotificationResolver` 负责，不把多条金额求和。

### 2.2 页面节点与公共字段

源码：[PageSnapshot.kt](../app/src/main/java/com/controleco/app/capture/page/PageSnapshot.kt)、[PageParseSupport.kt](../app/src/main/java/com/controleco/app/capture/page/PageParseSupport.kt)。下文 `|` 表示相邻文本节点，不是原文中的分隔符。

- `snapshot.lines` 按节点顺序取有效文本、去掉连续重复；节点的 `text` 优先，为空才取 `contentDescription`。`joined` 是它们用空格连接的全文。前两个节点、前八个节点等限制均针对 `lines`，不是屏幕像素位置。
- `isStatusTitleNode` 去掉行内货币金额和末尾标点后，要求整行等于状态词；“提交订单 支付成功 商家接单”不是标题。
- `nonResultPageReason` 排除消息中心、至少三个首页入口词、列表组合、锚点前后两行内的相对时间词，以及节点数 ≥30 且锚点下标 >8 的深埋状态词。**只有调用此函数的分支才有这些守卫**。
- `pickPaidAmount`：锚点内货币金额 → `PAID` 上下文 → 以货币符号开头的金额节点 → `ORDER_TOTAL` → `UNKNOWN`。分类依据主要是金额所在行；分开的标签和值另靠 `amountAfterLabel` 处理。它不会计算“原价减优惠”。
- `pickRefundAmount`：先取 `REFUND`，再取 `UNKNOWN`；不是只接受显式“退款金额”。两者都从含货币符号的金额集合中选择。
- `amountNearAnchor`：默认锚点及前后各一行，按分值去重，必须恰好一个非零金额；`5.2` 与 `5.20` 算同一个。支持独立数字、元后缀、货币符号与下一节点数字分开；货币符号位于窗口末行时也会读取其下一节点。
- `amountAfterLabel`：结构化快照先试同行及同父节点后续兄弟，再回退文本版的同行／标签后两行。商户等文本用 `valueAfterLabel`，不能用它代替金额函数；文本版可越过无效节点向后寻找有效值。
- 时间先按标签取值，再扫描全页首个完整日期时间，使用设备时区。标签按**页面出现顺序**搜索，不是固定优先“收款时间”；支持带年份的 `2026-10-06 12:34[:56]` 等格式。
- 微信、云闪付、电商的普通详情分支使用 `isStaleDetail`：`captureTime - txTime > 24小时` 才拒绝，时间缺失不判旧。成功页、独立退款分支、通用解析器没有统一的这道检查；支付宝直接拒绝详情页。

通知／银行文本／通用页面有 1000 万元上限，专属页面并未统一套用此上限。金额字段保存正的分值，收支方向和退款标志单独保存；微信详情的显式正负号另作方向线索。

## 3. 微信

修改入口：[WechatPageParser.kt](../app/src/main/java/com/controleco/app/capture/page/WechatPageParser.kt)；通知仍在 `NotificationRules`。

### 3.1 通知

身份闸门查 `title + text + bigText` 中的“微信支付”。联系人聊天即使含“消费＋金额”也不能绕过；支出词及金额式只认三种已确认写法。收入和退款使用第 2 节共同规则。

**真机来源回归：自动扣费。** [NotificationRulesTest](../app/src/test/java/com/controleco/app/capture/NotificationRulesTest.kt) 的 `wechat auto deduction with grouped count prefix`，注明 2026-10-22 用户实测：

```text
package = com.tencent.mm
title   = 微信支付
text    = [11条]微信支付: 已扣费¥6.50
bigText = 空
```

先通过身份闸门、去计数；“已扣费”确定支出；没有“元”结尾，走货币符号兜底。断言：`EXPENSE / 650分 / isRefund=false`，键为 `com.tencent.mm|EXPENSE|650|postTime分钟桶`。11 是消息数，不是金额。

### 3.2 页面：按顺序执行

1. 微信主壳 → 红包领取页 ASK → 聊天页 → 其他红包页。
2. 失败 → 取消 → 收银台，仅记录状态或上下文。
3. 列表 → 退款 → 详情 → 支付成功 → 收款到账 → 转账。

红包封面判断在聊天判断之前，是为了保留叠在聊天上的领取窗口；主壳判断仍更早。普通详情、支付成功和收款不是相互独立并行运行的规则，前面的分支命中后就返回。

| 分支／方法 | 触发条件与金额、方向 |
| --- | --- |
| `successCandidate` | “支付成功／付款成功／支付完成／付款完成／已支付”位于前两个节点，全文无“当前状态”；通过页面形状检查，状态不像标题时还需付款方式／完成等结果锚点。取 `pickPaidAmount`，再试“付款金额／金额”标签；正金额生成支出 |
| `detailCandidate` | 标题“账单详情／交易详情／转账详情／收款详情”加至少一个正文锚点；或无标题时，正文锚点至少两个、成功／退款状态、含货币符号的金额命中数 ≤2。锚点为“当前状态／交易状态／交易单号／商户全称／商户单号／收款方” |
| 详情金额与方向 | 前八节点的带符号独立金额（跳过优惠分类）→ 前八节点以货币符号开头的金额 → “金额／交易金额／付款金额／支付金额／实付款” → 公共实付兜底。前三者标记锚定，最后兜底不锚定。退款优先收入；否则显式 `-` 为支出、`+` 为收入；无符号才按“收入／已存入”判收入，其他为支出 |
| `receiveCandidate` | 先命中“你已收款／已收钱／收款到账／已存入零钱／待确认收款／收款成功”，且无“对方已收钱／待收钱／等待对方／零钱明细／交易明细／账单列表／收支统计”；还需至少两个结果标记。金额必须通过 `amountNearAnchor`，否则拒绝，生成收入 |
| `transferCandidate` | 锚点有“转账成功／已转入／已转出／零钱提现／充值成功／提现成功／到账成功／零钱通”。收入条件为“已转入／转入到零钱通”，或同时“转账＋已收款”；支出条件为“已转出／零钱提现”，或“转账成功且不是收入”；方向不明拒绝。金额用 `pickPaidAmount`，邻域检查只设置 `amountAnchored`，不是强制准入条件 |
| `refundCandidate` | “退款成功／已全额退款／退款到账”，或“退款”加“退款金额／退款单号／退款状态／退款方式”。用 `pickRefundAmount`，输出收入和 `isRefund=true`。该分支没有再验证退款最终完成状态，也没有旧详情时间检查 |
| `redPacketClaimResult` | 含“红包”，且“红包封面／回复表情到聊天／了解红包封面”至少两个；排除发红包词，封面首锚点前两行至后三行不能有已领取／详情等标记。取首个“元”行附近金额；缺失可为 0。只生成 `requiresUserConfirmation=true`、`tradeState=UNKNOWN` 的收入 ASK 候选 |

收款结果标记包括收款短语，以及“资金已存入零钱／收款时间／账单详情／零钱余额／转入零钱通”；按词表条目数计数，包含关系的短语也分别计数。“待确认收款”目前确实在锚点表中，不能把文档改写成只认“已完成收款”。

详情状态判定会把“当前状态／交易状态”本身当作成功线索，前面优先排除失败、取消、待付款、待支付、处理中等情况。普通详情再过待支付组合和 24 小时闸门；不要把这一实现描述为严格读取“当前状态”的值等于“支付成功”。

商户优先取公共商户标签，再从状态锚点后猜测；收款／红包另从“来自 X／X 向你转账／X 的红包”等提付款方。支付工具优先标签，再试“已选择 X”，最后用当前流程的收银台工具。业务时间优先页面时间，否则使用与采集时刻同一天的流程锚点。

## 4. 支付宝

修改入口：[AlipayPageParser.kt](../app/src/main/java/com/controleco/app/capture/page/AlipayPageParser.kt) 和 `NotificationRules.parseAlipayPointsExpense`。普通通知使用共同方向／金额式；“向你付款”优先于普通“付款”。

**支出积分专用通知规则（2026-11-05）：** 仅对 `com.eg.android.AlipayGphone` 生效，在通用噪声过滤前依次对归一化后的 `text`、`bigText` 做完整匹配：

```text
[可选的“交易提醒”前缀]你有一笔<金额>元的支出，点击领取<整数>个支付宝积分。
```

支持千分位、全角数字归一化、中英文逗号和可省略的句末标点。只取“你有一笔…元”中的金额，要求 `0 < 分值 <= 1_000_000_000`，固定输出支出、非退款，规则名 `支付宝·支出积分提醒`，去重键沿用普通支付宝支出格式。一般营销通知仍经过原过滤，不把“支出”加入全局确认词；不完整句式或额外营销前后文不属于此专用模板。

真机来源回归 `支付宝支出积分提醒_真实52元样本不被营销词过滤` 使用用户在 2026-11-05 提供的标题“交易提醒”、正文“交易提醒 你有一笔52.00元的支出，点击领取9个支付宝积分。”，断言支出 **5200 分**、`isRefund=false` 和上述规则名。测试见 [NotificationRulesTest](../app/src/test/java/com/controleco/app/capture/NotificationRulesTest.kt)，另覆盖长正文、金额范围、其他来源与相似营销反例。

### 4.1 页面规则

1. 前两个有效文本节点中至少一个以“支付成功”开头，取最先命中的节点作为标题；第三个及更后才出现则拒绝。
2. 全文出现“账单详情／交易详情／当前状态／创建时间／交易单号”即拒绝，避免历史账单中的状态文字成单。
3. 金额先取实际成功标题内的货币金额；否则从该标题的下一节点起找第一个金额，支持 `￥ | 9.17`；标题前的节点不参与金额提取。无货币符号的独立数字必须有小数点；负号开头节点不取。
4. 向后找金额时遇到“订单金额／付款方式／优惠／立减／红包”即停止。金额必须大于 0；成功标题为 `支付成功￥0.00` 时不回退取后面的原价，无论标题是第一个还是第二个节点。
5. 商户：先滤掉“获得森林能量／恭喜你获得／去领取／碰一下立减”，再从标题后最多六个节点找首个非金额、非“回首页”、非重复标题的文本，遇明细标记停止，截至 30 字。
6. 支付方式：只认独占一行的“付款方式”的紧邻下一行，交给 `PaymentInstrumentParser`；不猜其他标签。

产出固定支出、规则 `支付宝·付款成功页`，`txTime=null`、无页面订单号。解析器不使用收银台时间锚点；后续时间兜底由采集中心完成。首页、收银台、收款、转账、退款和详情页均不在当前页面识别范围；专属解析器拒绝后也不走通用兜底。

| 分支 | 当前条件／行为 |
| --- | --- |
| 还款排除 | “本次还款金额／本期账单／立即还款”命中至少两个，仅场景，不生成消费候选 |

## 6. 京东、淘宝、抖音、美团、饿了么

全部页面规则在 [CheckoutPageParser.kt](../app/src/main/java/com/controleco/app/capture/page/CheckoutPageParser.kt)，由公共方法加各应用 `CheckoutProfile` 配置组成。通知共用第 2.1 节的电商确认短语闸门，**不读取页面 profile 的词表**。

### 6.1 公共页面流程

按顺序：失败 → 取消 → 待支付 → 收银台 → 列表 → 退款 → 成功 → 收款 → 详情。

- 各 profile 的待支付词一旦命中就先返回；公共“去支付＋订单金额”等组合也先返回。不能因为同页还有成功词就假设一定进入成功分支。
- 收银台要求命中确认词，但没有成功词、详情标题、订单编号、交易单号。记录金额、商户、工具、时间，不单独生成候选。
- 列表检查公共组合和“全部订单＋待评价／待收货”等组合；还排除同时含多个货币金额、长节点中的成功状态。
- 成功锚点是首个包含成功词或自动扣款词的节点。像标题则通过这层判断；不像标题须有结果锚点并满足位置限制；随后仍调用 `nonResultPageReason`。
- 成功金额 `successAmount`：锚点内金额 → 按下标 `-1、+1、-2、+2` 依次找 `UNKNOWN／PAID` 行的货币金额或元后缀金额 → “实付款／实际支付／付款金额／支付金额／订单金额”标签 → 公共实付 → 当前流程收银台金额。**邻近金额可以先于更远处实付标签命中**，不是全页先找实付，也不校验该邻域只有一种金额。
- 成功候选固定支出，自动扣款词命中时场景为 `AUTO_DEBIT`，否则 `PAYMENT_SUCCESS`；规则名仍是“来源·支付结果页”。
- 详情须有 profile 详情标题，再有订单号、支付／付款／下单／交易时间、付款／支付方式、实付款之一；`detailTradeState` 为 SUCCESS 后取公共实付并过 24 小时闸门。“付款方式／实付款”本身也可作为成功线索；成功分支比详情更早。
- 退款默认标记“退款成功／退款到账／退款金额／已全额退款”，另接受“退款＋退款去向”等组合；取公共退款金额，生成退款收入。没有额外完成状态或旧账检查。
- 当前五个 profile 的 `receiveAnchors` 都为空，公共 `receiveCandidate` 没有被它们启用。

商户：profile 标签 → 公共锚点猜测 → 锚点后五节点扫描 → 收银台商户；支付工具：公共标签 → 长度 ≤16 的节点尝试工具解析 → 收银台工具。时间：页面时间 → 当天收银台锚点。

实现边界：详情候选若全文含“收入／退款”会设置收入方向，但 `detailCandidate` 的 `dedupKey` 当前仍按 `EXPENSE,false` 构造；独立退款分支则使用收入和退款键。修规则时需要同时核对候选与键，本文保留实际行为，不将其改写为已统一。

### 7.2 共用文本解析顺序

1. 归一化；先提尾号，再遮罩，避免尾号被当成金额。
2. 银行名先查括号签名，再全文查别名，最后用调用方的 `fallbackBankName`。已知 App 可用包名映射补银行名。
3. 噪声过滤：银行 `hardNoise`（验证码、密码、额度、分期、基金、到期、退订等）命中即拒绝；促销词仅在没有银行确认短语时拒绝；还需通过 `NotificationRules.isNoise`。
4. 方向：退款／退回／冲正优先为退款收入；其他按银行 `incomeWords` 与 `expenseWords` 判定，双向或都无则拒绝。银行“还款”属于支出词，不能与云闪付页面的还款排除混为一谈。
5. 扫描金额：含币种／元／圆标记，或数字自身含小数点才可能是金额；范围同通知。看匹配前 **10 个字符**：含余额／可用／剩余／额度／限额／欠款／当前／存款等就排除；优先首个带交易词的候选，否则首个非余额候选。
6. 提商户／渠道、尾号、账户标签，输出 `BankLedger`。来源键短信为 `SMS:…`、推送为包名；通道合并另行处理。

尾号只认“尾号／末四位／末4位／后四位／卡号后四位＋四位数字”或至少三个 `*／x／X` 加四位数字；不认“您账户2532”。商户依次尝试“商户名称：…”、“在…消费／刷卡／支付”、“向／付给／转账给…付款／转账／支付”、“支出／消费／收入／存入(…)”、“渠道／支付方式：…”；过滤纯数字和单独动词。

### 7.3 真机来源回归：工行交易金额与余额

[BankLedgerRulesTest](../app/src/test/java/com/controleco/app/capture/BankLedgerRulesTest.kt) 的 `真实样本_工行盒马支出3640`，注明 2026-10-27 真机捕获：

银行签名确定工行，“支出／消费／支付”确定支出，36.40 是非余额金额；7.62 的前文含“余额”而被排除。测试断言：


## 8. 银行页面通用兜底与不支持的应用

源码：[GenericPageParser.kt](../app/src/main/java/com/controleco/app/capture/page/GenericPageParser.kt)。当前银行页面没有专属解析器，使用这一实现：

1. 来源须属于已知支付／电商包名或已知银行包名，且注册表未选择专属解析器。
2. 先排除失败、取消、待支付、收银台、列表。
3. 要么有标题式成功词，要么有“账单详情／交易详情／订单详情／支付详情”；再通过页面形状检查，且结果锚点命中至少两个（支付方式、时间、单号、完成、查看订单等）。
4. 含退款／退回则用退款金额并标退款收入；否则含收入／收款／到账为收入，其余支出。金额用公共方法，范围 `0 < 分 <= 1_000_000_000`。
5. 置信度固定 MEDIUM。没有专属详情状态函数和 24 小时旧详情检查；详情标题可以代替成功标题，不应描述为“始终要求成功标题”。

成功词表为“支付成功／付款成功／支付完成／付款完成／交易成功／扣款成功／消费成功／下单成功／充值成功／提现成功／转账成功／还款成功／收款成功／已支付”。因此转账、还款等仍按上述文字方向输出收入或支出，不生成专门的账户间转账类型。业务时间取页面时间或 `flow.anchorTime`；这里没有专属解析器的同一天锚点检查。

普通回归 `目录内其余应用走兜底解析器_未知包名不处理` 断言 `cmb.pb → GenericPageParser`、`com.example.notes → null`。当前它验证的是分派，没有以招行成功页面节点验证金额提取。

**真机来源反例：拼多多。** [PageParserRegistryTest](../app/src/test/java/com/controleco/app/capture/page/PageParserRegistryTest.kt) 的 `拼多多不再解析_真实误记账样本不会生成候选`，注明 2026-10-19 补贴弹窗：正文含“本单已省14.99元”“拼单成功”“本单获得福建地区补贴”“26.80元”。断言无专属／兜底解析器，整页返回 `NotATradePage`。当前行为是移除来源，不是通过金额规则从该弹窗识别出消费。

## 9. 如何修复和补充规则

1. 从捕获日志取完整通知字段或页面节点，记录包名、App 版本、通道、捕获时间和交易时间；脱敏名称／单号时保留节点顺序、金额关系和必要身份关系。
2. 先在本页对应的测试类加入原始回归用例，写清样本来源及预期。分别断言是否产候选、金额分、方向、退款标志、商户、工具、时间；红包另断言 `requiresUserConfirmation`。
3. 按失败层改最小范围：通知改方向与金额式；某一电商的词表改 profile；某一 App 的特殊版式放专属解析器；确为公共问题才改 `PageParseSupport`。状态分支先后顺序也属于规则。
4. 为本次问题补相邻反例：优惠／余额／尾号、待付款／失败／列表、旧详情、多个金额、重复采样。改标题位置或兜底时尤其要验证此前拒绝的页面仍被拒绝。
5. 跑解析及合并相关测试，再同步本页规则与证据状态。没有真机成功样本时保留缺口，不以注册表测试代替；需要改变业务意图时先确认。
