# 自动记账捕获机制（设计说明）

> 本文档记录我ECO自动记账链路的机制设计、方案取舍与实测依据，与实现同步维护。
> 实现细节与验证记录见开发日志同日系列条目；通道状态见开发方案 §9。
> 版本：2026-10-16（页面采集层架构重构）。

## 一、机制速览

捕获链路是「系统通知监听 + 无障碍页面采集 + 银行动账短信」三通道合一，每条通道走同一条下游：
原始快照落库（不解析）→ 规则/解析器 → 统一交易候选 → 跨渠道融合 → 待确认队列 / 自动入账 / 悬浮确认卡。

| 维度 | 本项目的选择 |
|---|---|
| 采集主力 | 通知监听（微信/支付宝/云闪付/银行 App 推送/电商收银台）+ **无障碍页面采集**（支付结果页/账单详情页，字段最全）+ 银行动账短信（无任何 App 通知时的唯一线索） |
| 页面识别 | **按包名分派的应用专属解析器**（`capture/page/`）：每个应用独立识别页面场景与交易状态，不再是"所有应用共用一套关键词规则" |
| 应用覆盖 | 30 个应用的监听目录（支付/银行/电商三组），逐应用可开关；目录开关对**页面通道同样生效**；专属解析器覆盖 9 组包名（见第六节矩阵），其余目录内应用走保守兜底解析 |
| 入账方式 | 捕获**先直接入账**（三种方式任一开启即入账）；悬浮窗入账在此基础上弹卡：改完关掉卡片即同步修改、点「忽略」删除这笔；入账提醒发「已记入一笔账」通知；自动入账不打扰；三个全关才退回待确认队列 |
| 来源优先级 | **页面 > 通知 > 短信**：同一笔被多个通道捕获时只落一笔账，字段按"页面优先"逐字段合并（见第三节） |
| 确认前防错 | 五层：页面场景/状态闸门（待支付、失败、取消一律不生成候选）→ 内存 10s 重发窗口 → 合并池双向融合（页面⇄通知 10s；美团外卖重捕 3 分钟；**同流程/同通知实例才互并**；跨应用必须有支付渠道或银行卡线索）→ 自动入账前 ±60s 同数据库预检 → 入账再以去重键唯一索引兜底 |
| 归类学习 | 确认/保存时按商户名回写规则（下次自动预填分类/账户），条目封顶 500 条 |
| 账户匹配 | **支付工具 → 账户**：页面解析出的"招商银行(1234)"/"零钱"/"美团月付"参与账户匹配（卡尾号唯一命中优先），匹配不到才回落渠道默认 |
| OCR / 截图 | 不做（本地优先、轻量约束；也避免引入图像识别依赖） |
| 保活 | 通知监听自愈（收通知即自愈 + 分级重连）+ 更新后重授权提示 + 分品牌保活页引导 |

## 二、页面采集层（无障碍）架构

调用链只有一条，不存在第二个页面解析入口：

```
AccBookAccessibilityService      事件合并 → 稳定性补采 → 结构化快照（PageSnapshot）
        ↓  （文本 / 控件 id / 类名 / 层级 / 窗口）
PageParserRegistry.parse         按包名分派专属解析器（找不到专属解析器才落兜底解析器）
        ↓  （PageCandidate：字段 + 场景 + 交易状态 + 置信度 + 流程标识）
CaptureCenter.handlePageSnapshot 留样 → 跨渠道融合 → 直接入账 / 待确认
```

### 2.1 采集能力（与 `accessibility_service_config.xml` 一一对应）

| 能力 | 配置位 | 实际用途 |
|---|---|---|
| 多窗口读取 | `flagRetrieveInteractiveWindows` | 支付成功页可能是 dialog/非焦点窗口，不会成为 `rootInActiveWindow`；采集时活动窗口优先，再补同包名其余窗口 |
| 不重要视图 | `flagIncludeNotImportantViews` | 部分支付页把金额/商户节点标记为 `importantForAccessibility=false`，不开读不到 |
| 控件 id | `flagReportViewIds` | 快照保留 `viewId`（已截 `包名:id/` 前缀），作为文本定位的补充证据 |
| 事件节流 | `notificationTimeout=100` | 系统级第一道闸；服务内另有事件合并与稳定性补采 |

刻意**不申请**手势、按键、截图能力；快照按事件包名过滤，不读取其他应用的窗口内容。
服务启动时会把上述标志再确认一次（部分 ROM 会忽略 XML 里的部分位），并打印实际生效的标志位便于排查。

### 2.2 采样策略（替代"固定延迟 + 长时间指纹去重"）

1. **事件合并**：140ms 内的连续事件只采一次（事件风暴只取最后一个稳定状态）；
2. **稳定性补采**：首采后若内容仍在变化，按 320ms 间隔补采，最多 4 轮——支付成功页常有"结果先出来、
   明细后渲染"的过程；连续两轮内容一致即视为已稳定；
3. **空树补采**：窗口切换过渡期读到空树时限次（3 次）补采，仍为空则记日志放弃；
4. **去重只做短窗口**：同内容重复上报只在 2.5 秒内抑制（纯粹的防抖），**不再**"60 秒内同内容一律跳过"——
   那会把同额的第二笔真实交易吞掉；
5. **真正的去重靠三层**：解析器的流程上下文（同一页面实例只生成一次候选）、跨渠道融合（同一笔只落一笔账）、
   去重键唯一索引（数据库兜底）。

有界性：单次快照节点数上限 700、深度上限 40，遍历防环；解析在 IO 线程完成，事件回调里只做有界的控件树读取。

### 2.3 页面快照模型

`PageSnapshot` 保留 **节点层级**（父节点下标）、**控件 id**、**类名**、**文本与无障碍描述**、**窗口 id/类型**、
事件类名与该应用的当前活动名、采集轮次。解析器既可以用有序文本序列做位置运算（结果页版式稳定），
也可以在需要时按控件 id 或层级定位（改版后按 id 更稳）——不再只有"一坨扁平字符串"。

## 三、多来源融合（页面优先）

### 3.1 统一候选与逐字段优先级

三个通道的捕获结果都归一到同一形态（金额/方向/商户/时间/支付工具/来源/状态/去重键），
不存在"某条通道绕过融合直接写账"的路径。字段级优先级：

| 字段 | 优先级 |
|---|---|
| 金额 | 页面（实付类标签 → 独立金额节点 → 订单金额）> 通知 > 短信 |
| 商户 | 页面（标签 → 锚点后名称 → 收银台页记下的）> 银行侧 > 空 |
| 支付方式 / 支付工具 | 页面 > 银行侧卡信息（仅当页面没有时） |
| 交易时间 | 页面明确时间 > 通知发布时间（页面用捕获时刻兜底时）> 捕获时刻 |
| 关联标识 | 页面交易单号/订单号（可获得时）> 页面流程身份 / 通知实例身份 > 去重键 |
| 已入账条目的用户手改 | **最高**：用户改过的金额/商户/时间/备注/账户不再被自动富化覆盖；页面只能补空白的支付工具 |

### 3.2 页面与通知的几种时序

- **通知先到、页面后到**（最常见）：通知创建条目 → 页面在窗口内到达时按"页面优先"合并
  （金额/商户/支付方式/支付工具以页面为准），**不产生第二条**；页面迟迟不来时通知候选按设置正常入账。
- **页面先到、通知后到**：页面创建条目 → 通知命中同一笔时只补**缺失**字段（当前只补交易时间，
  比捕获时刻更接近真实支付时刻），不覆盖页面已确认的信息，也不产生第二条。
- **通知已入账、页面随后出现**：页面命中同笔的 AUTO 条目后回填更全的信息（写回交易本身），
  不重建交易；用户手改过的条目只补空白字段。
- **跨应用链路（电商/外卖页面 + 微信/支付宝/银行动账）**：包名不同也能关联，但必须存在
  **可核对的线索**——页面支付方式写着"微信支付/支付宝/花呗/余额宝"、或写着对应的银行名/卡尾号，
  且金额、方向、退款标记一致、时间相差 ≤130 秒。只凭"金额相同 + 时间接近"**不合并**。
  页面与通知双向都走同一套证据判定；线索不足或候选不唯一时保留独立记录。
- **同一笔的后续详情页**：页面流程身份相同的条目不受时间窗口限制（结果页之后再打开账单详情仍是一笔）；
  跨应用合并后条目可能保留通知来源包名，因此流程身份匹配不再要求来源包名相同。

### 3.3 同额两笔独立交易不能被并成一条

交易身份分三层，且**第一次生成就持久化**，不依赖内存缓存：

- **页面流程身份**（`p:<uuid>`）：同一次支付流程的确认页/结果页/详情页共享；用户再次进入收银台、
  或结果页终结后离开又完成一笔时重新生成。完整 UUID，不用短哈希；
- **通知实例身份**（`n:<sha256>`）：同一 `StatusBarNotification`（key + 原始发布时间 + 方向）的更新/重复回调共享；
  另一条通知即使同分钟同额也不同。刻意不含金额——同一条通知从"金额待补"更新为完整金额时仍是同一实例；
- **银行事件身份**（`b:<sha256>`）：同一条短信/推送的重复投递相同，不同事件/卡尾号分开。

这三类身份分别持久化到 `pending_transactions.flowId / notificationInstanceId / bankInstanceId`，
去重键只在数据库唯一约束层面追加对应后缀（`…|678@p:<uuid>`）。因此：

- 融合时**属于另一页面流程 / 另一通知实例的既有条目不参与合并**；跨通道时对侧身份为空，允许融合；
- 同一分钟内两笔同额交易拥有不同身份后缀，第二笔不会被唯一索引吞掉；
- 进程重启后，通知/银行重复投递仍能按持久化实例身份认回；页面详情页另有"明确交易时间相差 ≤30 秒"的兜底；
- 金额不同时**任何一层都不合并**——"候选唯一"不能证明是同一笔，宁可保留两条待确认。
- 无法判定归属时宁可保留两条待确认（用户丢弃一条的代价 < 丢一笔记录）。

### 3.4 时间、金额与写入一致性

- **通知时间**：优先 `notification.when`（显示时间），为零/未来/一天前时回落到
  `StatusBarNotification.postTime`，两者都异常才用采集时刻；异常时间不参与分钟去重桶。
  折叠摘要补全时使用子通知自己的系统发布时间。
- **通知重发判定**：重发窗口的键 = 通知实例 key + 原始发布时间 + 文本。应用更新同一条通知仍会被抑制；
  另一笔同额交易换了实例/发布时间则不会被静默吞掉。
- **银行整数金额**：`人民币50元`、`¥50元`、`50元`、`人民币1,234元` 都能识别；
  余额/额度/日期仍按上下文排除，余额-only 短信不入账。
- **写入一致性**：正式交易与 AUTO 关联条目在同一 Room 事务里插入；关联条目唯一键冲突时抛异常回滚交易插入，
  不会留下"有账单、无关联条目"的半成品。账户回填、待确认合并、撤销/编辑也都在事务内完成。
- **用户编辑保护**：用户手改后，自动富化不改金额/商户/时间/备注/规则名，也不自动改账户；
  只允许补空白支付工具。正式账单与待确认条目使用同一份合并结果。

## 四、支付方式 → 实际记账账户

以前只知道"这笔从微信付的"，于是所有微信支付都记到"微信"账户。现在页面解析出的**支付工具**
（零钱/零钱通/余额宝/花呗/招商银行(1234)/美团月付…）会参与账户匹配：

1. **卡尾号唯一命中**（"招商银行(1234)" → 名字含 1234 的账户）：同名银行的多张卡只有尾号能区分；
2. 账户名精确相等（标准化后比较，简称"招行卡"↔"招商银行"归一）；
3. 银行名 + 尾号同时命中；
4. 银行名/产品名包含匹配（唯一命中才算）；
5. 渠道兜底（零钱 → 名字含"微信"的账户；余额宝/花呗 → 名字含"支付宝"的账户）。

**匹配不到就用渠道默认账户，绝不猜一个不存在的账户**；匹配依据只有结构化后的支付工具，
备注里的"支付方式 X"文本不参与账户匹配。只保存卡尾号（后四位），不保存完整卡号。

页面/银行在通知入账**之后**补充支付工具时，会重新计算正式账单的账户，但有三道限制：

1. 只在支付工具能**唯一、明确**匹配到现有账户时才更新（银行卡带尾号时只认尾号唯一命中，
   尾号对不上不按银行名猜；银行卡也不回落到"渠道账户"）；
2. 用户已手改过的条目（`userEdited`）不自动改账户；
3. 账户更新与待确认条目回填在同一数据库事务里完成，账户余额/统计由 Room 自动刷新。

## 五、明确不做的（附理由）

- **无障碍服务名伪装 / 声明为无障碍工具**：靠伪装成系统组件规避系统提示与用户感知，属欺骗性设计，不做。
- **截图 + OCR / 图像识别**：与"本地优先、轻量、可维护"冲突；页面读不到时就如实记为"未识别"，不换一条更重的路。
- **服务端 AI 归类 / 云同步 / 云规则**：本项目本地优先，架构上不引入。
- **5 秒自动确认倒计时、拖拽缩放卡片**：收益低、误操作风险高，不做。
- **全局常驻状态机**：支付流程上下文只保留"每包名一个、3 分钟超时"的短期缓存，不做全局状态机；
  但每笔交易的**身份标识**会随条目持久化（页面流程/通知实例/银行事件），用于进程重启后的防重。
- **邮箱中转、Excel 模板生成等导入玩法**：与本轮"捕获链路"无关。

### 6.2 兜底解析（未逐应用校准，不宣称已适配）

| 范围 | 解析器 | 行为 |
|---|---|---|
| 目录内其余应用（各银行 App 等） | `GenericPageParser` | 只认"标题式成功词 + 两个以上结果页锚点"的保守组合；命中即入账（置信度标注为中等），未命中仍留样本进捕获日志供后续扩规则 |

### 6.3 未覆盖 / 已知边界

- 目录内**银行 App 的页面**未做动账详情页适配：银行动账走通知与短信通道（见通知规则维护指南）。
- 微信零钱通/理财通的转入转出页面、群收款（AA）页面：未实现专属场景，按兜底解析处理。
- 支付宝花呗分期、医保支付等组合字段未细化：金额取实付，其余字段可能缺失。
- 各专属解析器的样本以项目捕获日志与开发日志记录的真实页面为主，其余为版式推演样本；
  真机验收清单见开发日志对应条目——**在真机样本替换前，不把"有解析器"当成"已全面支持"**。

## 七、遗留与待验收（诚实记录）

- 银行短信/银行推送**没有真实样本**（仓库内只有微信/支付宝日志），规则按通用形态推演 + 合成单测，
  首条真实样本到手后按 `logcat -s ControlECO` 与捕获日志扩规则（见维护指南）。
- 电商/外卖与抖音、淘宝的页面版式未经真机验证，靠"场景 + 状态 + 标题位置"多重闸门保证宁漏勿错；
  均可在设置里逐项关闭（「监听的 App」）。
- 云闪付通知与银行短信这两种通道当前**不互相归并**（无法在不读卡号的情况下区分"同卡两通知"与"两卡同额"），
  宁可留两条待确认由用户丢弃，不冒并错的风险。
- 页面与通知的关联窗口为 10 秒（美团外卖结果页重捕为 3 分钟）：支付结果页的采集延迟通常在 1 秒内，
  超出窗口的极端慢渲染场景会各自成条，由用户丢弃一条——不为了合并而扩大"同额即同笔"的口径。
- 跨应用关联（电商/外卖页面 ⇄ 支付通知/银行动账）依赖页面明确写出支付渠道或银行卡线索。
  这是有意的保守：没有线索时宁可两条待确认，也不冒"两笔同额交易并成一笔"的风险。
  真实样本仍待补充（见开发日志本轮条目），当前只以合成单测保护。
- 通知实例身份的边界：若应用复用同一个通知实例、同一发布时间、同一方向并发生两笔同额交易，
  系统侧没有更多可区分信息，可能仍被视为同一条通知。此类场景需要真实样本再评估。
- 页面流程上下文 3 分钟超时后，如果用户仍停留在旧成功页且页面发生重渲染，理论上可能被当成新候选；
  账单详情页有"明确交易时间 ≤30 秒"兜底，成功页没有更多可区分信息。正常路径会先出现收银台或用户离开页面，
  该极端场景需真机样本再评估。
