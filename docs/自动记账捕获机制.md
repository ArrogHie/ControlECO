# 自动记账捕获机制

核对基线见[文档索引](README.md)。金额统计见[金额与预算计算](金额与预算计算.md)，应用识别条件和测试示例见[逐应用解析规则](自动记账逐应用解析规则.md)，规则改动入口见[维护指南](通知规则维护指南.md)。本文描述实际调用链；源码中仍有少量 10／60／130 秒和旧“先确认后入账”的注释，不能用它们覆盖当前实现。

## 1. 入口与采集范围

| 通道 | 入口 | 前提与范围 |
| --- | --- | --- |
| 通知 | `NotificationCaptureService → CaptureCenter.onNotificationPosted` | 系统通知使用权；支付／电商通知须规则认识来源且用户开启监听；银行推送另受银行推送开关和已知银行包名限制 |
| 页面 | `SelectToSpeakService → AccBookAccessibilityService → onPageCaptured` | 本应用无障碍服务、页面采集开关和监听来源；按包名分派解析器 |
| 银行短信 | `SmsCaptureReceiver → onSmsReceived` | RECEIVE_SMS、短信采集开关；仅新到短信，号码／银行正文线索过滤，多段短信合并 |

`isCaptureEnabled`（界面“自动记录收款 / 动账通知”）实际约束通知、页面与短信三个入账入口；页面、银行推送、短信还各有子开关。采集总开关、页面、银行推送、退款提醒、金额待补录默认开启；银行短信默认关闭。开关默认值不等于已经获得系统授权。

通知源为微信、支付宝、云闪付，以及 `NotificationRules.checkoutPackages` 中电商／外卖来源；银行推送必须命中 `BankLedgerRules.bankAppPackages`，正文出现银行名不足以让未知 App 入账。全量通知记录只增加原始样本，不把未知 App 变成银行候选。全量页面记录则绕过监听目录过滤：总开关与页面开关仍开启时，规则认识的来源可能继续生成候选；页面子开关关闭时只留样，不能笼统把全量页面开关说成永远不入账。

监听目录以 [CaptureAppCatalog.kt](../app/src/main/java/com/controleco/app/capture/CaptureAppCatalog.kt) 为准。页面专属解析器有微信、支付宝、云闪付、京东、淘宝／天猫、抖音、美团／美团外卖、饿了么八组；其余接受的来源走 `GenericPageParser`。列入目录与有兜底解析均不代表全部支付场景已适配。

页面读取可访问节点，不进行截图 OCR、自动点击付款或读取支付 App 私有数据库。Manifest 只注册一个入口子类 `com.google.android.accessibility.selecttospeak.SelectToSpeakService`，实现仍在本应用采集服务；历史设备验证见[兼容性记录](无障碍页面捕获兼容性.md)。

## 2. 从样本到候选

### 通知与银行文本

通知收集标题、正文、长正文、附加文本、Inbox／Messaging 明细；缺金额的分组摘要可从同组子通知补明细。不会把多条消息里的金额相加记成一笔。

`NotificationRules.parse` 先校验来源并归一化文本／遮罩卡尾号，尝试支付宝支出积分专用模板；未命中时继续微信支付身份校验→噪声与红包过滤→电商确认短语→方向→金额：

- 支付宝正文或长正文完整符合“你有一笔xx元的支出，点击领取x个支付宝积分”时，专用规则直接提取支出金额；可带“交易提醒”前缀，规则名为 `支付宝·支出积分提醒`。金额仍受通知范围约束，其他营销过滤不变。
- 微信标题或正文须含“微信支付”；微信支出仅认“已支付／已扣费／自动扣费”等当前专用词，不用泛化“消费”抓聊天或营销。
- 退款优先判为收入；收款短语可压过付款字样，其他方向冲突会放弃。
- 金额先尝试“金额在动词前”的反向匹配，再方向专用正向匹配，最后在方向成立时取货币符号金额。不是简单取第一个数字。
- 通知金额范围为 `0 < 分值 <= 1_000_000_000`（1000 万元）；不要把该上限说成所有页面解析器和导入共用的全局约束。
- 红包通知不走普通解析或缺金额补录。无金额退款也持久化为退款 PENDING 并发提醒；其他明确方向且开着金额待补录的通知可生成金额 0 的 PENDING。

银行短信／推送共用 `BankLedgerRules.parse`，识别银行、方向、退款、动账金额、商户和卡尾号；余额等上下文排除。银行侧来源采用 `SMS:银行` 或 App 包名，支付工具线索用于账户匹配。

通知业务时间依次取合理的 `notification.when`、系统 `postTime`、采集时刻；早于采集 24 小时、晚于采集 5 分钟或非正时间均视为异常。业务时间决定账单日期／分钟桶；同笔窗口通常使用首次实际捕获时间。

### 页面

采集事件先合并 140ms，再间隔 320ms 采样，最多 4 轮、连续 2 轮稳定结束；主树最多 700 节点／40 层，事件源补采最多 120 节点／16 层；短指纹缓存 2.5 秒。这些是采样控制，不是交易合并窗口。

`PageSnapshot` 保留文本节点、控件 ID、层级、窗口等证据；`PageParserRegistry` 按包名分派。解析返回无关页面、仅场景或候选，异常隔离为 UNKNOWN 场景。

支付宝付款成功标题允许位于前两个有效文本节点。依据是 2026-11-05 用户提供的真机快照：`「支付寶」的說明文字列。 | 支付成功￥52.00 | …`；金额从命中的成功标题及其后方提取。完整样本与回归用例见[逐应用解析规则](自动记账逐应用解析规则.md)。

各解析器按自身的成功、收款、退款或详情条件产生候选；待支付、失败、取消、列表、首页、聊天等由对应分支排除，不能仅凭页面含金额推导入账。部分退款分支接受“退款金额”等字段，没有另查最终完成状态。微信、云闪付和电商的普通详情分支在交易时间早于捕获超过 24 小时时拒绝；独立退款分支和通用解析器没有这道检查，支付宝直接不识别详情页。具体分支顺序与限制见逐应用规则。

公共实付金额优先级是：锚点内金额→实付类上下文→独立货币金额节点→订单总额→未知上下文；排除已分类为优惠、余额、费用等的候选。各专属解析器还有独立闸门，退款另走退款金额提取，不能宣称任意页面都能准确取得实付。

`PageFlow` 按应用维护流程，使用 `p:<UUID>` 身份。终结后重新进入收银台开启新流程；没有收银台时，同一已生成页面要在终结、确实离开、离开后至少 5 秒的条件下才可重新生成。加载过渡页不算离开。流程上下文是最后活动后 180 秒过期，**与下节固定首捕窗口不是同一个计时方式**。

## 3. 同笔识别与字段合并

### 3.1 身份和持久化

普通去重键基本形态：

```text
来源|方向[|R]|金额分|业务时间分钟桶[@身份]
正式账单 externalId = NTF:<dedupKey>
```

`p:` 页面流程、`n:` 通知实例、`b:` 银行事件分别比较；同一应用同类身份不同通常视为独立交易。跨应用的页面 UUID 不直接互相比相等。分钟桶只是键的一部分，不是“同分钟同额一律合并”。

`pending_transactions.dedupKey` 与 `transactions.externalId` 均有唯一索引。直接入账时正式交易和 AUTO 关联条目在同一 Room 事务中插入；关联条目插入冲突会回滚，避免半条记录。

### 3.2 固定首捕窗口

常规捕获合并常量均引用 `LogicalTransactions.CAPTURE_WINDOW_MS=180_000`。同应用、支付／银行、跨应用、同银行匹配使用首次条目的 `createdAt` 等首捕锚点；回填业务时间、后续捕获、用户确认不会重新延长三分钟。

- `LogicalTransactions` 保存已吸收来源、键别名及 HANDLED／REJECTED 终态。确认或忽略后，在窗口内仍能识别迟到事件，只记溯源，不重新建账／弹卡。
- 普通重复合并必须金额分、方向、退款标记一致；金额冲突不能靠“页面更权威”强行合成一笔。
- 统一逻辑匹配和跨应用／支付银行配对要求唯一候选；但同应用 `pickRelatedPending` 取窗口内最近匹配，同银行 `BankEventClaims` 也择最近候选。不能概括成所有路径都“多候选不合并”。
- 终态、别名、字段锁和银行通道登记是内存状态，重启会丢失；Room 中仍存在的 PENDING／AUTO 身份和唯一键提供部分保护，不是持久化完整交易状态机。

### 3.3 来源配对规则

| 配对 | 当前规则 |
| --- | --- |
| 同应用通知／页面 | 同方向、同金额、退款标记兼容、身份兼容，常规窗口 180 秒 |
| 微信⇄银行短信／推送 | 仅支出，金额、时间和退款标记匹配；不要求银行卡线索 |
| 支付宝／云闪付⇄银行 | 同上，额外要求支付文本包含银行名／卡尾号，或银行文本点名该支付渠道 |
| 微信⇄支付宝⇄云闪付 | 不因同额而互相归并 |
| 同银行短信／推送／页面 | 银行名归一、金额／方向／退款相同、尾号双方都有时相等；收入也适用 |
| 不同银行 | 不作为同银行事件归并 |
| 电商／外卖来源⇄微信／支付宝 | 金额／方向／退款一致，排除资金操作和商户冲突；订单号或渠道线索优先，同额退路还检查明确渠道冲突；两档均为 180 秒 |
| 电商／外卖来源⇄银行／云闪付 | 需订单号或匹配的银行／卡尾号等证据，不走微信／支付宝的纯同额退路 |

`CrossAppLinker.Evidence.isCheckoutPage` 实际按来源是否在电商包名表判断，不检查原始采集通道；因此其中“页面侧”也可能是该来源的通知条目。同订单号在硬条件后优先返回，早于渠道冲突退路，不能写成所有证据档都先校验渠道冲突。

云闪付在支付银行去重中属于支付侧，在跨应用链路分类中属于银行侧，不能混用这两套分类。

同银行 `BankEventClaims` 按通道登记，每条关联对同一通道最多吸收一次，配对取最近的可用条目；登记是内存机制。另有统一逻辑匹配回退，不应把 1:1 登记写成所有银行相关匹配的全局保证。

弱线索的同额合并有误并边界；身份不兼容、证据不足、窗口外或重启后也可能保留重复条目，不保证全局绝不重账／漏账。

### 3.4 时间、金额与写入一致性

180 秒不是所有防重机制的统一寿命，页面还存在不依赖首捕窗口的强匹配：

| 机制 | 判定 |
| --- | --- |
| 通知重复回调抑制 | 通知实例、原始时间和全文相同，10 秒内抑制 |
| 持久化通知／银行实例 | 既有 PENDING／AUTO 实例及金额、方向、退款一致可直接判重 |
| 稳定页面缓存 | 有明确交易时间的页面，包名＋方向＋退款＋规则＋金额＋交易时间相同，首次观察后 5 分钟；不续期 |
| `pickRelatedPendingForPage` | 先匹配同来源同额、交易时间差 ≤60 秒；再同订单号；再同流程；之后才常规窗口 |
| `pickByExplicitTime` | 显式交易时间差 ≤30 秒的补充匹配；前一步已有 60 秒路径，不能称整体只有 30 秒 |

因此不能承诺“180 秒后一定新建”或“不同流程的同额记录绝不合并”：页面时间／订单匹配优先于流程隔离。

确认为同笔后，页面可回填商户、备注、支付工具和业务时间，并同步 AUTO 对应正式账单。重复通知不覆盖完整页面商户；普通重复合并只补空商户／支付工具、组合备注，不改金额／时间。银行信息通常补账户线索，可信工具匹配后可修正账户。

悬浮卡按金额、商户、备注、分类、账户逐字段登记编辑保护；未编辑字段仍可补全，旧 `userEdited=true` 条目继续整条保护。新字段锁只在进程内有效；编辑捕获账单也按实际改动登记相同字段保护。

## 4. 入账、提醒与待确认

普通金额完整候选，且能找到分类／账户时：

```text
普通交易直接入账 = 自动入账 || 悬浮窗入账 || 入账提醒
捕获退款 = 始终先进入待处理
```

三个开关全关才保留待确认。直接入账成功保留 AUTO 关联；已合并／已处理结果直接返回，不能再按“入账失败”插第二条 pending。分类／账户缺失或写入失败等返回空结果时回落待确认。

默认自动入账与入账提醒开启，悬浮窗入账关闭；自动入账与悬浮窗模式互斥。普通卡优先，未展示时回落通知，通知仍受入账提醒和系统通知授权限制。

| 场景 | 关闭／超时 | 忽略／撤销 |
| --- | --- | --- |
| 已入账普通卡 | 保留账单；有效编辑同步 | 删除账单和 AUTO 关联 |
| 未入账普通卡 | 金额／分类／账户有效则确认，否则保留待确认 | 丢弃条目 |
| 微信红包 ASK 卡 | 只收起，保留待确认 | 丢弃条目 |

普通弹卡延迟 3 秒，红包询问 600ms，无交互关闭 60 秒，“已记入”撤销条停留 6 秒。展示还检查悬浮权限、本应用是否前台、亮屏／锁屏和前台来源；未知前台、系统界面、支付上下文和银行来源有各自放行条件。本应用悬浮窗发出的窗口事件不再覆盖真正前台来源，应用退出／无障碍断开会清理陈旧前台状态。SavedState 在挂载前初始化；仅首次绘制后登记已展示，挂载失败或 500ms 内未绘制时最多尝试 3 次、间隔 1 秒，最终按设置回落通知。首次绘制只能证明窗口绘制，不能证明机型支付保护层上一定可见。

### 特殊候选

- **金额 0 占位**：仅表示待补录，不能直接入账。补录校验正金额及通知上限，更新去重键后仍待确认；后到完整候选会清理相近的同来源同方向占位。此清理不等于占位已有精确订单身份。
- **微信红包 ASK**：领取页特征命中后，金额仅作预填，可能为空。ASK 独立键为 `ASK|包名|r:页面流程:指纹摘要`；不进 PENDING／AUTO 合并池，不受“全部确认”处理，用户明确确认才落账。同流程同封面重复采样抑制，并非每次事件都弹卡。
- **有金额退款**：所有通道均先写退款 PENDING，通知和列表打开 `refundLink/{pendingId}`，选中同金额原支出后才生成收入。退款不会进入普通悬浮确认卡或“全部确认”。
- **无金额退款**：同样持久化为金额 0 的退款 PENDING；通知关闭／重启仍可在列表处理。同一通知实例后到完整金额时回填既有条目；普通缺金额记录的清理不会误删退款。退款提醒开关只控制通知，不丢弃待处理记录。具体人工规则见[业务文档](业务与数据模型.md)。

## 5. 分类与账户

普通自动入账分类：已学商户规则→商户关键词→备注关键词→同方向“其他”→同方向首项；普通收入始终排除“退款”分类。规则执行全角与标签归一但不模糊匹配分店名，一次学习即生效。自动入账、待处理和批量确认加载同一规则；商户后到会更新未被用户修改的分类，有效分类不会因空线索退回“其他”。退款收入仅在用户确认原支出后生成，不参与商户学习。

初始账户：存在的学习账户→支付工具解析匹配→银行名／别名→来源关键词→首个账户。来源关键词为微信、支付宝，其余兜底“银行”，不是所有商家都自动建独立账户。

支付工具匹配实际顺序是：唯一卡尾号→唯一银行＋尾号→归一化名称精确→唯一银行／产品包含匹配→渠道兜底。账户必须已存在，不自动创建。

后到页面／银行信息更新账户用更严格的 `trustedAccountId`：银行卡带尾号只接受唯一匹配尾号；无尾号工具按解析器匹配，银行卡不接受仅渠道兜底；匹配不到不改账户。用户锁定账户时不自动改写。

## 6. 日志、保留与代码入口

捕获日志用于原文／未匹配样本，溯源用于解释入账／合并／重复等处置；两者都不是正式账单。溯源默认关，不追溯补记。通过 `dedupKey → NTF:dedupKey` 关联当前账单状态。

初始化清理：捕获日志删除 7 天前记录，再保留最新 2000 条；溯源保留最新 1000 条；AUTO 关联删除 24 小时前条目；商户规则最多 500 条（学习时也清理）。这些是清理执行时的策略，不是后台实时定时保证；正式账单不会随 AUTO 关联清理而删除。

主要实现：
