# 11 · 待确认账单

自动捕获（通知/页面/短信）先落到待确认列表，用户逐条确认分类/账户/商户或丢弃；0 元占位条先补金额；微信红包必须逐条确认，不参与一键确认。

**同一页还有第二类条目**：已入账、但还没处理的退款收入（`refundPending = 1`）。它和捕获条目**并进同一个列表，不单独分区**（产品要求）；处理方式见 [12-退款关联](12-退款关联.md) 第 7 节。

源码：`app/src/main/java/com/controleco/app/ui/pending/PendingScreen.kt`（约 910 行）

---

## 1. 路由与入口

- 路由：`pending`。
- 进入：
  - 个人页「待确认」椭圆 → `pending`
  - 设置 → 开发者功能 → 待确认账单
  - 通知 `ROUTE_PENDING`
- 离开：返回。
- 本页不导航到编辑；确认/丢弃/补金额都在本页 sheet 内完成。

## 3. 页面骨架

```
Column(fillMaxSize)
  EcoTopBar(micro="PENDING", title="待确认账单", onBack,
            action = confirmableCount>0 ? "全部确认" : {})
  if (entries.isEmpty())
    Box(weight 1f) EcoEmpty("没有待确认账单", ...)
  else
    LazyColumn(weight 1f, padding 22/top 8/bottom 32)
      if amountMissing>0  PendingWarning(amber)
      if askCount>0       PendingWarning(clay)
      if refunds>0        PendingWarning(blue)
      items(entries)       PendingRow / RefundPendingRow + EcoRowDivider(0)
      item summary         "共 N 条，M 条可一键确认，K 条退款待处理"

confirming?.let ConfirmPendingSheet
amountEditing?.let PendingAmountSheet
linking?.let RefundLinkSheet(候选同金额、未标已退款的支出)
incomeAsk?.let EcoConfirm("记为收入")
if (confirmAllAsk) EcoConfirm("全部确认")
```

`entries` = 捕获条目 + 退款条目，按 `sortAt` 倒序**混排**。捕获条目用 `createdAt`；
退款条目也用**入库时间**（`TransactionRow.createdAt`），这样几个月前捕获的退款也会浮到顶部。

## 5. 状态与数据流

### 只读

`pendingList`、`pendingRefunds`、`accounts`、`categories`。

### 统计

- `amountMissing = pending.count { amountCents <= 0 }`
- `confirmableCount = pending.count { status != ASK && amountCents > 0 }`
- `askCount = pending.count { status == ASK }`
- `refunds` = `vm.pendingRefunds`（`refundPending = 1` 的退款收入）

`confirmableCount` **只数捕获条目**：退款待处理不参与「全部确认」。

### 本地

`confirming`、`amountEditing`、`confirmAllAsk`、`linking`、`candidates`、`linkError`、`submitting`、`incomeAsk`。

### 行点击

- 金额缺失 → 打开补金额 sheet。
- 否则 → 打开确认 sheet。

### 确认 sheet

- 默认分类：`vm.guessCategoryId(type, counterparty.ifBlank { note })`。
- 默认账户：`vm.guessAccountId(sourcePackage, ruleName, paymentInstrument)`。
- 可改：商户、分类（同类型）、账户。
- 入账 → `vm.confirmPending(item, categoryId, accountId, counterparty)`。
- 分类/账户为空 → 错误，不提交。

### 补金额

- 输入金额 > 0 → `vm.setPendingAmount(id, cents)`；回调 message 非空时系统 Toast。
- 两条路径：通知栏直接回复「输入金额」，或本 sheet。

### 丢弃

`vm.discardPending(id)`，**无二次确认**（轻量操作）。

### 退款待处理（第二类条目）

行点击 / 「选择原账单」→ 打开 `RefundLinkSheet`：

- `LaunchedEffect(linking?.id)` → `vm.refundExpenseCandidates(row.amountCents)`，**只列同金额、且还没标「已退款」的支出**。
- 点一个候选 → `vm.handlePendingRefund(refundId, expenseId)`：
  - 成功：把那笔支出标 `REFUNDED_EXPENSE`、这笔退款 `refundPending = 0`（**两笔记录之间不写任何关联**）、`EcoToast("已标记为已退款")`、关闭 sheet、该行因 Flow 刷新自动消失；
  - 失败（退款已处理过、支出已标过已退款等）：错误显示在 sheet 内。
- 原支出标上 `REFUNDED_EXPENSE` 后**不再计入支出**（含分类预算）。
- 「记为收入」→ `EcoConfirm` → `vm.markRefundAsIncome(refundId)`：
  清掉 `refundMark / refundPending`，按普通收入记账；原支出保持原样，**照常计入支出**。
- 候选为空时给空态：`没有同金额的支出账单`，引导「记为收入」。

### 全部确认

- 只对 `status != ASK && amountCents > 0` 的条目生效；**退款待处理不参与**（正文里说明）。
- 确认前 `EcoConfirm`，正文说明：按默认分类（其他）与推测账户入账，之后可在流水中修改；金额待补的不会被确认。
- 确认 → `vm.confirmAllPending()`。

## 6. 交互

| 操作 | 结果 |
| --- | --- |
| 点行（有金额） | 确认 sheet |
| 点行（缺金额） | 补金额 sheet |
| 行内「确认」 | 确认 sheet |
| 行内「补金额」 | 补金额 sheet |
| 行内「丢弃」 | 直接丢弃 |
| 退款行点行 / 「选择原账单」 | 选被退款账单 sheet（同金额、还没标已退款的支出） |
| 候选支出点一下 | 标原支出「已退款」→ Toast → 行消失 |
| 退款行「记为收入」 | 二次确认 → 记账为普通收入 |
| 顶栏「全部确认」 | 二次确认 → 批量入账（不动退款） |
| 确认 sheet「入账」 | 校验 → 入账 → 关闭 |
| 补金额「保存」 | 校验 → 保存 → 关闭 |

## 7. 文案

- 顶栏：`PENDING` / `待确认账单`；`全部确认`。
- 空态：`没有待确认账单` / `开启通知监听后，收款/动账通知会出现在这里`。
- 警告：
  - `有 N 条金额待补录：点「补金额」输入，或从通知栏通知直接回复（「全部确认」会跳过它们）`
  - `有 N 条微信红包待确认：请逐条确认是否记账，不参与「全部确认」。`
- 行：`金额待补`、`收款方 X`、时间、`待补`/`红包`/`待确认`、`补金额`/`确认`、`丢弃`。
- 汇总：`共 N 条，M 条可一键确认`（有退款时追加 `，K 条退款待处理`）。
- 退款警告条：`有 N 条退款待处理：选中被退款的支出后，那笔支出会标记为「已退款」，不再计入本月支出与分类预算。`
- 退款行：`+X`、`退款到账 微信支付/支付宝/通知捕获/银行动账/手动记录`、商户、时间、`待处理`、`选择原账单`、`记为收入`。
- 退款 sheet：`选择被退款的账单`；`退款 +X，商户，时间`；`选中后，那笔支出会标记为「已退款」，不再计入本月支出与分类预算。`；`同金额的支出账单`；`加载中…`；`没有同金额的支出账单`；空态补充 `可以「记为收入」：这笔退款按普通收入记账，对应的支出不会被标记为已退款。`；`记为收入`/`取消`。
- 记为收入确认：标题 `记为收入`；正文 `这笔退款按普通收入记账；对应的支出不会被标记为已退款，仍计入本月支出。之后不会再出现在待处理里。`；`记为收入`。
- 确认 sheet：`确认支出/收入 X`；`收款方 / 商户`；`例如：美团外卖`；`分类`；`账户`；`暂无分类，请先在分类管理中添加`；`暂无账户，请先在账户管理中添加`；`取消`；`入账`；错误 `请选择分类`/`请选择账户`。
- 补金额：`补录支出/收入 金额`；`金额（元）`；`0.00`；`两条路都行：下拉通知栏点「输入金额」直接回复，或在这里补。`；`取消`/`保存`；错误 `请输入有效金额`。
- 全部确认：`全部确认`；正文 `将把 N 条按默认分类（其他）与推测账户入账，之后可在流水中修改。另有 M 条金额待补录，不会被确认。K 条退款待处理不会被动到。`；`确认`。
- Toast：`已标记为已退款`、`已记为收入`。

## 9. 坑与验收

**坑**

1. **红包（ASK）不参与「全部确认」**；`confirmableCount` 必须排除 ASK 和 0 元。
2. 0 元占位条不能直接确认，必须先补金额；点行也要进补金额，而不是确认。
3. 「全部确认」会用默认分类“其他”+ 推测账户，正文必须说清楚，且提示可之后修改。
4. 丢弃没有二次确认；不要“顺手”加确认弹窗改变手感。
5. 分类只显示与交易同类型的；收入单不能选支出分类。
6. 默认分类/账户是“推测”，可能为空；为空时必须要求手选。
7. `sourceLine` 要去重：来源标签与规则名重复时只显示规则名。
8. 补金额保存后列表项金额变化，但不会自动打开确认 sheet；需再点一次。
9. 顶部 `全部确认` 只在 `confirmableCount>0` 时出现；不要恒定显示。
10. **退款条目不能并进「全部确认」**：它是已入账的记录，只需要选中被退款的支出；混进批量确认会算错条数。
11. 退款条目和捕获条目**同列表混排、不分区**（产品要求）；新增条目类型沿用 `PendingEntry` 的 key 前缀，避免 LazyColumn key 冲突。
12. 退款行按**入库时间**排（`createdAt`），不是业务时间；否则几个月前捕获的退款会沉到列表底部找不到。
13. 处理完不要再手动从本地列表移除行：`pendingRefunds` 是 Flow，`refundPending = 0` 后自动消失。
14. 「记为收入」会改历史数据（`refundMark = NONE`、`refundPending = 0`），先弹 `EcoConfirm`；不要静默执行。
15. 退款候选**只列同金额、且还没标「已退款」**的支出（产品口径）；不要加"展开全部支出"，那是另一个产品决定。
