# 11 · 待处理

源码：`ui/pending/PendingScreen.kt`。路由 `pending`；业务规则见[业务与数据模型](../业务与数据模型.md)，退款候选见[退款处理](12-退款关联.md)。

## 列表

普通捕获、红包 ASK、新捕获退款与更新前的已入账待处理退款合并为一个列表，按 `createdAt` 倒序。不分区，不添加说明小字；空态「暂无待处理账单」。

| 条目 | 操作 |
| --- | --- |
| 普通金额齐全捕获 | 确认、丢弃 |
| 普通缺金额捕获 | 补金额、丢弃 |
| 微信红包 ASK | 逐条确认、丢弃 |
| 新捕获退款（含无金额） | 选择原账单、丢弃 |
| 更新前已入账待处理退款 | 选择原账单 |

新退款行使用「退款」标记，无金额时主金额位置显示「退款」，不要求先补金额。

## 普通确认

- 确认弹层包含商户、分类、账户；退款分类不可选。
- 默认分类与账户应用商户规则；将原商户、备注和收支方向传入推测函数。
- 订阅规则更新，规则晚于弹层加载时自动更新默认值；用户已经手动选择的字段不被覆盖。
- 普通缺金额条目输入有效正数后才能确认。金额输入使用 `EcoMoneyField`。
- 顶栏「全部确认」仅在存在金额大于 0 的普通 PENDING 条目时显示；跳过 ASK、缺金额和全部退款。
- 批量操作确认文字仅为「确认 N 笔账单？」；结果使用实际商户规则推测，不承诺统一归「其他」。

## 退款

新捕获退款通过 `onRefund(pendingId, null)` 进入全屏候选页；更新前已入账退款通过 `onRefund(null, refundId)` 进入兼容候选页。列表页不再保留旧退款弹层或「记为收入」操作。

## 验收

- 新有金额／无金额退款都能出现在列表，通知打开同一条待处理退款。
- 退款行不显示「补金额」或普通「确认」；批量确认不处理退款。
- 完成退款后列表与角标同步减少；未选择原账单返回时仍保留。
- 普通确认应用学习到的商户分类／账户，手动选择不被后到默认值覆盖。
- 列表采用单一 LazyColumn，长列表与大字号不被说明文案挤占。
