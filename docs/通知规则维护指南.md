# 捕获识别规则维护指南（通知 + 无障碍页面 + 银行动账）

> 目的：遇到识别不了（或不想再识别）的通知/页面/银行短信格式时，按本文档快速添加/修改/删除规则。
> 规则集中在 `app/src/main/java/com/controleco/app/capture/`：
> `NotificationRules.kt`（通知）、`page/`（无障碍页面：注册表 + 各应用专属解析器，见第五节）、
> `BankLedgerRules.kt`（银行短信与银行 App 推送，见第六节）、
> `CrossChannelDedup.kt` 与 `CaptureMerge.kt`（跨通道归并与页面⇄通知融合，见第七节）。
>
> **证据门槛：无明确证据的解析不允许加入。** 新增锚点/字段/方向词/排除词必须有可追溯的
> 真机样本、开发日志实测记录或旧版生产规则依据；不得从其他应用/其他实现的解析链直接搬词，
> 不得仅凭词义相似扩展。合成单测只能锁定已确定的行为，不能作为规则来源。
> 页面侧的具体约束见《自动记账捕获机制》§2.3。

## 一、标准工作流（遇到新格式）

1. **抓样本**：确保设置 → 自动记账 →「记录所有应用的通知」开着（debug 构建默认开）→ 触发目标通知 → 设置 → 捕获日志 → 找到该条 → **点击复制原文**（含 pkg/title/text/bigText）。
   - 也可 Logcat 过滤 tag=`ControlECO` 看 `onPosted pkg=... title=[...] text=[...] bigText=[...] postTime=...` 一行。
2. **定位失败原因**：捕获日志/Logcat 里三类失败输出对应三个修复点：
   | 日志输出 | 含义 | 修复点 |
   |---|---|---|
   | `skip (not interested) pkg=...` | 包名不在白名单 | 加 `knownPackages` |
   | `skip noise pkg=...` | 命中噪声黑名单（营销/物流/安全提醒） | 若确为交易，给 `confirmPhrases` 补该文案的确认短语 |
   | `rule ambiguous (both/none direction)` | 方向关键词没命中或同时命中收/支 | 调整方向关键词 |
   | `rule amount not found ...` | 方向对了但金额没提到 | 加/改正则 |
   | `rule amount out of range [...]` | 金额超上限（¥1000 万）被判误抓 | 检查样本是否把订单号/手机号当金额 |
3. **改 `NotificationRules.kt`**（见下文修改点清单）。
4. **固化测试**：把样本原文加进 `app/src/test/java/com/controleco/app/capture/NotificationRulesTest.kt`（一条真实样本一个用例）。
5. **验证**：
   ```bash
   gradle :app:testDebugUnitTest --tests "*NotificationRulesTest*"
   gradle :app:assembleDebug
   ```
   装机复测，确认待确认队列出现预期条目。
6. **记录**：git 提交（样本原文写进提交信息），docs/开发日志.md 记一条。

> 及时性提醒：捕获日志只保留 7 天 / 2000 条，原始样本过时会自动清掉——写规则前先复制原文。

### 附：回查"某笔账从哪来"——记账溯源（开发者功能）

排查"这笔入账当时是哪条通知/哪个页面、匹配到哪条规则、有没有被页面合并改写金额"时，用
设置 → 开发者功能 →「记录记账来源」**先开启**（默认关，只对开启后的新捕获生效），
之后到「溯源记录」页看：每条含通道/包名/时间/金额/处置方式（自动入账、入队、页面合并回填、
重复跳过、退款提醒）、账目状态（已入账/待确认/已丢弃）、规则名，展开即原始来源全文，可复制。
与捕获日志的差别：溯源**不含未识别样本**（那是捕获日志的活）、**滚动清理不掉**（封顶最近 1000 条）、
且每行能跳到对应账单——适合事后复盘单笔账，不适合当规则开发的样本池用。

## 二、引擎机制（30 秒版）

`NotificationRules.parse(pkg, title, text, bigText, postTime)` 处理流程：

```
包名在 knownPackages？
  → body = text + bigText
  → 方向判定（优先级：退款 > 收入 > 支出；收/支同时命中 = 放弃）
  → 金额提取三层：正向正则 → 反向正则 → ¥ 金额兜底
  → 产出 ParsedNotification(type, amountCents, ruleName, dedupKey, isRefund)
  → CaptureCenter 写入待确认队列（dedupKey 撞车则跳过）
```

- **方向关键词**（当前）：
  - 退款：`退款 / 退回`（优先级最高，"退款到账"不会被"到账"带偏）
  - 收入：`收款 / 到账 / 入账 / 收入`；收款码/转账入账短语 `向你付款 / 付款给你 / 转账给你 / 向你转账 / 收到一笔`
    （优先级高于泛化的“付款”；真实样本「收钱码 倩蕾通过扫码向你付款2.00元」曾因只命中“付款”被判成支出）
  - 支出：`已支付 / 支付成功 / 支出 / 消费 / 付款 / 扣款 / 支付凭证`
- **金额正则**（当前）：
  - 正向：`关键词后 0~8 个非数字字符 + 金额元`（金额必须带"元"收尾），如 `收款0.01元`、`成功入账100.00元`——防止把营销文案里的裸数字当金额（真实样本「…自动扣款支付，点击领取6个支付宝积分」曾把 6 当成金额）
  - 反向：`金额 + 元 + 最多8个非标点字 + 关键词`，如 `你有一笔14.90元的支出`、`你有一笔2.98元的免密/自动扣款支付`；标点（，。）是硬边界，营销文案在标点之后不会被反向正则跨越
  - 兜底：`¥12.80 / ￥12.80`（如微信「已支付¥12.80」）
- **dedupKey** = `包名|方向|R?|金额分|分钟` ——方向和退款标记必须在键里，否则同一分钟内"同额支出+退款"会互相吞掉。
- 金额只接受最多两位小数（`Money.parseCents` 限制），账单/通知里的金额都满足。

## 三、常见场景与改法

### 场景 A：已有 App 出了新通知写法（金额位置/写法变化）
1. 对照样本检查三层金额正则哪层没覆盖。
2. 优先把新关键词/写法**合并进现有正则**的交替分支（如 `(?:已支付|支付成功|支出|...)`），而不是另开一条规则。
3. ⚠️ 检查副作用：新关键词不能让**既有样本**的方向判定翻转。例：不能加裸词「支付」——微信收款通知里的「微信支付」会让收支双向命中而被放弃。

### 场景 B：新增支付/银行 App（新包名）
1. 捕获日志拿到确切包名（注意区分主包与推送子包）。
2. `knownPackages` 加包名；`sourceLabel` 加品牌显示名（显示在待确认列表和 ruleName 里）。
3. 先不动金额正则——通用三层（**反向/正向/¥ 兜底**，反向优先以避开关键词后的营销文案，如"支出，领1元红包"）常能直接命中；跑测试确认，不中再按场景 A 补。
4. 银行 App 常见格式参考：`您尾号1234的账户于…入账100.00元`（正向）、`消费50.00元`（正向）。

### 场景 C：金额藏在折叠通知（"[2条]…"）
- 监听服务已把 InboxStyle 明细行（EXTRA_TEXT_LINES）和消息样式（EXTRA_MESSAGES）并入 text——先看捕获日志里该条的 text 是否已包含含金额的明细行。
- 若明细行有金额：正则按明细行文本写即可。
- 若仍无金额（如微信退款汇总）：**保持不识别**（无金额不入队是预期行为），靠支付宝式单条退款通知或账单导入兜底；日志会明确输出「退款汇总通知常无金额，属预期」。

### 场景 D：停止识别某类通知（删除）
按粒度从大到小：
1. **整个 App 不再捕获**：从 `knownPackages` 移除包名（原始日志也不再记录）。
2. **某类方向不识别**（如不想让"付款成功"类进队列）：从对应方向关键词（如 `expenseHit`）删掉该词。注意确认不破坏其他样本。
3. **某条规则只入日志不入队**：让它解析不到金额即可（如退款汇总无金额的现状）——不要用异常/硬 return 破坏流程。
4. 删除后：把对应测试用例改为断言 `null` 或删除用例，跑全量测试。

### 场景 E：金额/方向都识别对了，但想改显示
- 待确认列表里的来源与类型显示 = `ruleName`（规范：`品牌·收款/入账 | 品牌·支出/消费 | 品牌·退款`）+ `sourceLabel`；改 `sourceLabel()` 与 ruleName 拼接处。
- 默认入账账户推测在 `LedgerViewModel.guessAccountId`（包名 → 账户名关键词），新支付 App 在这里加映射。

## 四、修改点速查（NotificationRules.kt 内）

| 要改什么 | 位置 |
|---|---|
| 包名白名单 | `knownPackages` |
| 方向关键词 | `parse()` 里的 `refundHit / incomeHit / expenseHit` 三行 contains 列表 |
| 正向金额正则 | `incomeAmount / expenseAmount / refundAmount` |
| 反向金额正则 | `reversedAmount`（金额+元+关键词，覆盖"14.90元的支出"） |
| ¥ 兜底 | `currencyAmount`（一般不用动） |
| 显示名 | `sourceLabel()`、ruleName 拼接 |
| 去重键 | `dedupKey` 拼接行（改格式时注意方向/退款段必须保留） |
| 退款入账口径 | `isRefund` → CaptureCenter 写 `REFUND_INCOME`（勿动，与账单导入口径联动"显示退款记录"开关） |

配套文件（一般不动）：
- `capture/CaptureCenter.kt`：重发去重窗口、白名单外是否记录、待确认入队。
- `capture/NotificationCaptureService.kt`：文本抽取（title/text/bigText/明细行/消息样式）。
- 测试：`app/src/test/java/com/controleco/app/capture/NotificationRulesTest.kt`。

## 五、页面识别规则（无障碍通道，capture/page/）

页面通道的规则不是"一套通用关键词"，而是**按包名分派的专属解析器**。结构：

| 文件 | 作用 |
|---|---|
| `page/PageSnapshot.kt` | 页面快照模型（节点层级 / 控件 id / 类名 / 文本与描述 / 窗口） |
| `page/PageParseSupport.kt` | 公共解析原语（金额上下文分类、标签取值、商户兜底、时间、页面形状闸门） |
| `page/AppPageParser.kt` | 解析器接口 + 结果类型 + 支付流程上下文（`PageFlow` / `PageFlowTracker`） |
| `page/PageParserRegistry.kt` | **按包名分派**（专属解析器 → 兜底解析器 → 不处理），异常在此隔离 |
| `page/WechatPageParser.kt` 等 | 各应用/同系列应用的专属解析器（覆盖范围见 `docs/自动记账捕获机制.md` §6） |
| `page/GenericPageParser.kt` | 兜底解析（目录内其余应用，判据更严：标题式成功词 + 两个以上结果页锚点） |

### 新增一个应用的步骤

1. **采样**：debug 构建 → 设置页打开「捕获所有页面（调试）」→ 真机走支付流程 →
   Logcat 过滤 `ControlECO` 看 `[Page] page matched / page scene / snapshot` 的文本快照；
   未识别页面也进捕获日志（标题「页面快照」，点击复制）。
2. **建解析器**：新建 `page/XxxPageParser.kt` 实现 `AppPageParser`（或在 `CheckoutPageParser` 上加一份 `CheckoutProfile`，
   电商/外卖同形页面用后者）；在 `PageParserRegistry.dedicated` 注册。
   解析器要给出：**页面场景**（结果页/详情页/收款/转账/退款/收银台/待支付/失败/取消/列表）、
   **交易状态**、**金额**（走 `PageParseSupport.pickPaidAmount`）、商户、支付方式（结构化 `PaymentInstrument`）、时间、单号。
3. **不要只加包名白名单**：只在注册表里加包名而解析器没有真实场景判定，等于"注册了但不支持"；
   包名清单以「监听的 App」目录（`CaptureAppCatalog`）为准，不另造一份。
4. **固化**：新快照 → 在 `page/` 下对应测试类加用例（照抄真机快照的节点顺序），全量回归。

### 微信页面规则（WechatPageParser）

- **聊天页不是结果页**：`PageParseSupport.looksLikeChatPage` 命中（聊天信息 + 输入栏特征，或输入栏至少两个特征）
  直接拒绝；历史转账气泡里的“已收款”、红包气泡里的“已领取”都不能单独成单。
- **收款金额必须锚定**：收款到账页要求 ≥2 个结果页标记（你已收款/收款时间/账单详情/零钱余额/转入零钱通），
  金额用 `PageParseSupport.amountNearAnchor` 取锚点行/相邻行的唯一金额；禁止整页第一笔金额兜底，
  邻域出现多个不同金额直接拒绝。
- **红包领取页只询问、不自动记账**：识别到领取页（红包封面/回复表情到聊天/了解红包封面 至少两个，
  且不是发红包页/已领取页）时生成 `requiresUserConfirmation` 候选，采集中心落一条 **ASK** 待确认并弹悬浮卡；
  用户点「记一笔」才入账、点「忽略」即删除、关闭卡片不入账。金额只是预填值，缺失时由用户补录。
  聊天页“你领取了…红包”、红包详情/结果页、发红包页一律不自动成单；通知侧的“红包到账/你领取了/收到红包”等
  红包语义也会被拦截，不走普通收款规则；转账仍保留自动记账。
- **无标题账单详情**：不依赖“账单详情/交易详情”标题，正文锚点（当前状态/交易状态/交易单号/商户全称/商户单号/收款方）
  ≥2 + SUCCESS/REFUND 即可；顶部裸负数 `-12.35` 按支出、`+` 按收入，保留 24 小时旧账闸门。
- **微信 8.0.52+ 节点树白名单**：`collect empty pkg=com.tencent.mm` 且 `uiautomator dump` 只有空根时，
  先确认系统读屏服务（随选朗读/TalkBack）已启用；这是外部限制，不是解析器异常。
  权限页「微信页面读取（随选朗读）」显示状态与步骤；冷启动权限提醒在页面采集且微信在监听范围时也会列出该项。

### 排查（Logcat 子标签 [Page]）

| 日志 | 含义 | 修复点 |
|---|---|---|
| `a11y event pkg=… type=… cls=…` | 事件到了（2 秒节流） | 事件没到 → 检查无障碍开关/包名是否被用户关掉 |
| `skip (app not watched) pkg=…` | 该应用不在监听目录（或用户关掉了） | 设置 → 监听的 App |
| `skip (a11y capture disabled)` | 页面通道开关关了 | 权限页「自动记录支付页面」 |
| `collect empty pkg=… give up` | 窗口内容不可读/未就绪 | 页面是否 WebView/支付保护层拦截 |
| `collect empty pkg=com.tencent.mm` | 微信节点树白名单/系统读屏服务未启用（8.0.52+） | 启用系统随选朗读/TalkBack；不是窗口未就绪 |
| `page scene pkg=… detail=<场景>/<状态> <原因>` | 页面被识别为交易场景但不生成候选 | 原因即解析器的拒绝理由（收银台/失败/取消/列表/无金额…） |
| `page matched pkg=… rule=… scene=… state=… ask=…` | 已生成候选 | 关注金额/商户/支付方式；`ask=true` 表示红包领取页，只会弹卡询问 |
| `queued red packet confirmation: #…` | 红包领取页已落 ASK 待确认并尝试弹卡 | 正常；卡片没弹会接横幅通知 |
| `ask card dismissed -> keep pending #…` | 红包询问卡被关闭/超时 | 正常：不入账，条目仍在待确认列表 |
| `skip duplicate stable page pkg=… rule=… txTime=…` | 同一带交易时间结果页重复采样，已跳过 | 正常（页面缓存去重，不是错误） |
| `parser failed pkg=… parser=…` | 解析器抛异常（已被隔离，不影响其他应用） | **修解析器**：异常绝不允许传播 |
| `skip identical page (…ms)` | 2.5 秒内的同内容重复上报 | 正常（防抖，不是去重语义） |

### 页面通道的关键约定（改规则前必读）

- **只有"已完成的交易"才生成候选**：收银台/待支付/处理中/失败/取消一律只更新流程状态，不生成候选；
  退款是独立资金流（收入方向 + 退款标记），不与同额消费互相覆盖。
  **唯一例外**是微信红包领取页：生成 `requiresUserConfirmation` 候选并落 ASK，由用户决定是否记账，绝不自动成单。
- **金额按上下文取**：`PageParseSupport.pickPaidAmount` 的优先级是"锚点节点内金额 → 实付类标签 → 独立金额节点 →
  订单金额 → 未知"，优惠/余额/运费/红包/退款上下文一律不参与；页面同时有订单原价与实付时永远取实付。
- **同一页面实例只生成一次候选**：解析器用 `flow.markEmitted(页面实例键)` 登记；
  **再次进入收银台 = 新的一笔**（`PageFlow.noteConfirmPage` 自动重置流程），同额的第二笔因此能重新成单。
  没有收银台的路径要求"结果页已终结 + 用户确实离开过（过滤加载/空白过渡页）+ ≥5 秒"才重新成单。
- **稳定页面缓存**：带页面交易时间的收款/详情候选在进程内缓存 5 分钟（包名+方向+规则+金额+交易时间），
  同一页跨分钟/流程重置再次采样时直接跳过；没有交易时间的成功页不缓存。进程重启或旧数据里已有
  同额同交易时间条目时，页面 txTime 在 60 秒内回并到既有条目，不再插 pending。金额不同绝不合并
  （CR-003；锚定金额也不改变这条）。微信红包领取页产生的 ASK 条目不在 `getMergeable()` 池里，
  也不参与“全部确认”，因此不会被同额转账/收款自动认领。
- **流程身份不能省**：`PageCandidate.flowKey` 只是展示用；真正的身份是 `PageFlow.flowInstanceId`（完整 UUID，
  `p:` 前缀）。采集中心把它写进去重键后缀与 `pending_transactions.flowId`，阻止"属于另一流程的条目"被合并——
  这是"同额两笔独立交易不会被并成一条"的基础。通知/银行另有 `n:` / `b:` 实例身份，三种身份互不阻塞跨通道融合。
- **金额不同绝不自动合并**：页面来源优先只决定字段取值，不能替代"是否同一笔"的判定；冲突只写日志。
- **异常隔离**：解析器里任何异常都会被 `PageParserRegistry` 吞掉并降级为"与交易无关"；
  写解析器时不要依赖"抛异常让上层跳过"。
- 纯金额节点不能当商户（`PageParseSupport.isAmountLikeNode`）、状态短语不能当商户/支付方式（`statusPhrases`）、
  "对方已收钱"是付款方的支出状态——这几条是页面解析的既有口径，别删。

### 美团 / 美团外卖的额外约束

- 结果页标题位置约束：`CheckoutProfile.titleAnchorMaxIndex = 2`——订单列表/订单进度条里也有"支付成功"；
- **月付支付**的结果页标题是"交易成功"（不是"支付成功"），两种都认；
- 外卖结果页**不展示商户**，商户固定为来源名"美团外卖"（`MeituanPageParser.merchantOf` 覆写）；
- 结果页会被弹窗干扰而**重新观察**：美团外卖有 3 分钟"重捕窗口"（**严格同金额**，见 `CaptureMerge`）。

### 页面通道与通知通道的差异

| 维度 | 通知通道 | 页面通道 |
|---|---|---|
| 采集范围 | 支付三包 + 电商收银台（确认短语闸门）+ 银行推送 | 监听目录内全部应用；8 组包名有专属解析器，其余走兜底解析 |
| 输入 | 标题+正文拼接 | 结构化快照（文本序列 + 控件 id + 层级 + 窗口） |
| 场景 | 无（只有确认短语闸门） | 结果页/详情页/收款/转账/退款/收银台/待支付/失败/取消/列表 |
| 金额 | 关键词后 → 反向 → ¥ 兜底 | 实付类标签 → 独立金额节点 → 订单金额（排除优惠/余额/运费） |
| 同笔判定 | 通知实例 key + 原始发布时间（重复回调）+ `n:` 实例身份；10s 跨通道窗口严格同金额 | 页面实例键（同页不重复成单）+ 流程身份 `p:`（同额两笔隔离，**仅同应用内**）+ 10s 跨通道窗口 |
| 跨应用 | 与商户页按 130s 明确线索 / 60s 短时同额判定（`CrossAppLinker`），流程身份不参与 | 与支付应用同上；同应用内仍按 `p:` 隔离 |
| 附加字段 | 无 | 商户 / 支付方式（含卡尾号）/ 交易时间 / 交易单号 |
| dedupKey 分钟桶 | 通知 postTime | 页面交易时间（无则捕获时刻）——同笔交易跨通道对齐 |

## 六、银行动账规则（BankLedgerRules.kt，短信 + 银行 App 推送）

银行动账**短信**与银行 App 的动账**推送**是同一种文本形态（`【工商银行】您尾号1234的储蓄卡
10月8日12:30消费人民币50.00元，余额5000.00元`），解析核心共用 `BankLedgerRules.parse()`。
两者入口不同：
- 短信：`SmsCaptureReceiver`（需「银行动账短信」开关 + RECEIVE_SMS 权限）→ `CaptureCenter.onSmsReceived`；
- 推送：通知监听通道里**不在支付白名单**的包名 → 签名/包名闸门 → `CaptureCenter.handleBankPush`。

### 排查（Logcat tag=ControlECO，子标签 [Sms]）

| 日志输出 | 含义 | 修复点 |
|---|---|---|
| `skip (not a bank message) sender=...` | 号码不在银行号码段且正文无银行签名 | 补 `bankSenderPrefixes`（确认为银行号码时） |
| `skip (no bank signature) [...]` | 正文与包名都认不出银行 | 补 `bankNames` 别名或 `bankAppPackages` 包名短名单 |
| `skip (noise) bank=...` | 命中硬/促销噪声黑名单 | 确认非交易；若是交易且带确认短语可补 `confirmPhrases` |
| `skip (direction unclear)` | 收/支方向词都没命中或同时命中 | 补 `incomeWords` / `expenseWords` |
| `skip (no amount) bank=...` | 金额提取失败 | 检查货币标记/小数点；余额上下文是否误伤 |
| `bank sms not matched (#id)` | 银行短信已进捕获日志但没解析出来 | 捕获日志拿原文，按上表逐项排查 |

### 修改点速查

| 要改什么 | 位置 |
|---|---|
| 银行名/别名 | `bankNames`（标准名 + 工行/招行等简称） |
| 短信签名 | `signatureRegex`（【…】/［…］） |
| 银行 App 包名短名单 | `bankAppPackages`（**只是兜底线索，不是闸门**——正文签名才是） |
| 银行短信号码段 | `bankSenderPrefixes`（前 5 位，含 +86 处理） |
| 方向词 | `incomeWords` / `expenseWords`（退款优先级在 `detectDirection` 里单独处理） |
| 金额上下文 | `balanceContexts`（这些词出现则不取）/ `ledgerContexts`（优先取） |
| 商户提取 | `merchantPatterns`（"在X消费"、"商户名称：X"…） |
| 噪声 | `hardNoise`（一票否决）/ `promoNoise`（需无确认短语） |

### 跨通道归并（CrossChannelDedup.kt）

银行卡绑定支付渠道时，一笔消费会同时产生支付通知 + 银行短信/推送 → 若不归并就是两条待确认。
判定在 `CrossChannelDedup.isSameTransaction`：金额分全等 + 方向相同 + 退款标记相同 +
时间差 ≤130s + **通道类别相异且一边支付类、一边银行类**。
- 通道类别表的维护点在 `channelClass()`：新增支付渠道（电商等）加进 PAY 分支之前，
  先确认不会与银行类误配（未知来源一律 UNKNOWN、不参与归并）；
- 归并后银行侧只追加账户线索到备注（`mergeBankInfoIntoPending`），金额/时间/方向一律以既有条目为准。
- 归并前必须存在可核对线索：支付类条目里有银行名/卡尾号，或电商页面支付方式指向该银行；
  只凭"金额相同 + 时间接近"不合并（`CrossChannelDedup.hasBankEvidence` / `CrossAppLinker`）。
- 通知时间优先 `notification.when`，异常时回落 `StatusBarNotification.postTime`，再回落到采集时刻；
  异常时间不参与分钟桶。重发抑制键包含通知实例 key 与原始发布时间，不能只看文本。

### 跨应用关联（CrossAppLinker.kt）

电商/外卖页面与支付应用（微信/支付宝）是两条链路：真实顺序固定为
**微信/支付宝先捕获（页面或通知）→ 用户返回商家应用 → 商户结果页再捕获**。

判定分两档，改动点在 `CrossAppLinker.linkReason`：

| 档位 | 条件 | 窗口 |
|---|---|---|
| 明确线索 | 订单号相同；或页面支付方式写着"微信/零钱/分付"⇄微信、"支付宝/花呗/余额宝"⇄支付宝、对应银行名/卡尾号⇄银行动账 | 130 秒 |
| 短时同额 | 页面读不到支付方式时，两条链路捕获到**完全相同金额** | 60 秒 |

两档共用的硬闸门（任一不满足即不合并）：
- 必须恰好一侧是电商/外卖页面、另一侧是支付应用（同额档）或支付/银行（强证据档）；
- 金额分、方向、退款标记全等；
- 双方都有商户名时至少一方包含另一方（"美团" ⊂ "美团外卖" 可以，"肯德基"/"麦当劳" 不行）；
- 页面明确写出的渠道与对侧来源冲突时不合（页面写支付宝 ⇄ 微信通知）；
- 充值/提现/转账/还款不参与；
- 同一应用内的两笔同额订单仍由页面流程身份隔离（`flowCompatible` 的 `incomingPackage`）。

日志：命中写 `[Dedup] cross-app same transaction ... reason=...`，未命中但窗口内有同额候选写
`[Dedup] cross-app same amount kept separate ...`（说明是哪道闸门挡住的）。排查时先看这两行。

> 页面流程身份（`p:<uuid>`）**按应用分别生成**：微信的 `p:x` 与美团的 `p:y` 永不相等。
> 因此 `flowCompatible(..., incomingPackage)` 跨应用时不拿它否定同一笔；
> 同一应用内仍按流程身份隔离两笔同额订单。

### 真机样本要求（重要）

`BankLedgerRulesTest` 的样本目前是**按通用形态推演的合成串**（该通道还没有真机样本）。
首次收到真实银行短信/推送后：按上表把原文加进测试用例（改名标注来源），再按需扩规则——
这比事后追查错账便宜得多。

## 七、悬浮确认卡排查（Overlay）

捕获入队后会优先弹「悬浮确认卡」（底部卡片，需悬浮窗权限），弹不出来才回落横幅通知。
排查"为什么没弹卡/为什么没提醒"时的日志特征（Logcat 过滤 `ControlECO`，子标签 `[Overlay]`）：

| 日志输出 | 含义 | 处理 |
|---|---|---|
| `confirm card shown` | 卡片已展示（抑制了同笔横幅） | 若屏幕上看不到 → 支付保护层/系统拦截，见权限页教程（小米还要看「后台弹出界面」） |
| `confirm card unavailable, fallback to notification` | 显示条件不满足或 addView 失败 | 看前一行：无权限/锁屏/本应用前台/前台应用与来源不一致，均按预期回落通知 |
| `card collapsed, fallback to notification` | 用户收起或 60 秒无操作 | 预期（保留待确认 + 补发通知） |
| `confirm card auto dismiss` | 无交互超时收起 | 预期 |
| 无任何 `[Overlay]` 行且只有通知 | 开关关 / 无悬浮窗权限 / 屏幕熄灭 | 权限页检查「悬浮确认卡」section |

排查工具：开发者功能 →「悬浮确认卡（立即）/（延迟 20 秒）」；**Toast 可见而卡片不可见 = 卡片被
支付保护层拦截**（Toast 是系统级窗口，不受支付保护影响）。

## 八、注意事项（踩坑记录）

1. **关键词改动的副作用**必须用全量既有测试回归（250+ 用例就是样本库）。
2. 方向歧义时引擎**主动放弃**（宁漏勿错），漏掉的会留在捕获日志——不要为了"抓到"放宽到双向命中仍入队。
3. 金额正则新分支要考虑小数与整数千分位：只可能遇到 `100` / `100.00` / `¥1,234.56` 三种（Money 已处理千分位逗号）。
4. 每条真实样本 = 一个测试用例，命名写清来源与格式特征（如 `alipay expense with amount before keyword`）。
5. 改动提交后同步更新 docs/开发日志.md：样本原文 + 失败原因 + 修改点，方便日后回溯。
