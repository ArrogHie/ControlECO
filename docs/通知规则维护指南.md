# 捕获识别规则维护指南

核对基线见[文档索引](README.md)。本页只维护修改入口与验证方法；当前入账、窗口、红包和账户语义统一见[自动记账捕获机制](自动记账捕获机制.md)，各 App 的条件、金额提取及已运行示例见[逐应用解析规则](自动记账逐应用解析规则.md)。

## 1. 先定位失败层

| 现象 | 首先核对 |
| --- | --- |
| 完全没有原始样本 | 权限、服务连接、通道开关、监听来源、系统后台限制 |
| 有样本，无规则命中 | 原文是否有成功／到账证据、金额、方向；包名和场景是否受支持 |
| 解析成功但没新增账单 | 合并／重复／终态、ASK、待补金额、分类／账户缺失与写入失败 |
| 金额或方向错误 | 金额上下文、退款优先级、通知正文拼接、页面节点顺序 |
| 同笔重记 | 首捕时间、p/n/b 身份、订单／页面时间、候选数量、进程重启及最终保留键 |
| 账户错误 | 学习账户、支付工具、尾号与账户命名、初始兜底或后到可信回填 |
| 未弹卡／通知 | 入账与提醒分别检查；悬浮权限、亮屏／前台条件、入账提醒及系统通知权限 |

全量通知只扩展留样；全量页面会绕过监听目录过滤，若总开关和页面子开关仍开启，受支持解析器仍可能生成候选。只采页面样本时保留总开关、关闭页面子开关，详见捕获机制。溯源需事先开启；日志中金额、商户等可能含隐私，测试样本使用脱敏值。

排查时记录：包名、通道、规则名、原文或节点、业务时间、首次捕获时间、金额分、方向、退款标记、身份、dedupKey、PENDING／AUTO／ASK 状态、处置结果。只看最终账单金额不足以定位合并问题。

## 3. 解析规则约束

- 通知方向与金额必须一起维护。微信支出专用词为“已支付／已扣费／自动扣费”；金额反向表达式也须与此对应，不能把营销尾部“消费”重新纳入。
- 通知金额实际为反向→正向→货币符号兜底；不能把银行卡尾号、积分、优惠门槛当金额。明确成功交易可能携带营销尾巴，正反样本都要测试。
- 页面先判断场景／状态，再取金额；不能用“关键词＋任意金额”跳过列表、聊天、待支付和旧详情闸门。
- 微信收款页必须通过锚点邻域的唯一金额检查；微信转账页的邻域检查只设置 `amountAnchored`，实际取值仍可走公共实付兜底。维护时按分支核对，不能把收款限制当成所有转账规则的现状。
- 金额一致是常规合并前提；`mergePageInfo` 有覆盖能力不代表调用者可合并不同金额。
- 红包通知、聊天红包与领取页 ASK 是不同路径；ASK 必须继续隔离自动合并与批量确认。
- 相同订单号、页面明确时间和流程身份各有匹配顺序；改动时验证强匹配先于常规 180 秒窗口的影响。
- 用户编辑过的商户／备注不再作为原始渠道证据；编辑保护按字段生效，并非整条禁止补全。
- 初始账户兜底与后到可信账户回填是两套要求；不能用首个账户兜底覆盖已经入账的账户。
- 解析置信度是候选信息，当前普通直接入账不以统一置信度阈值分流；不要仅因“低置信度”就描述为一定待确认。

## 4. 样本与验证

先把脱敏原文或完整页面节点写成回归样本，再改规则。保留包名、顺序、上下文、窗口及必要时间关系；注明实测或合成，不把合成文本称为真机验证。

| 变更 | 现有测试入口 |
| --- | --- |
| 通知解析／折叠 | `NotificationRulesTest`、`NotificationRulesHardeningTest`、`GroupNotificationResolverTest` |
| 银行动账 | `BankLedgerRulesTest`、`BankEventDedupTest`、`CrossChannelDedupTest` |
| 页面 | `PaymentPageParserTest`、`WechatPageRegressionTest`、`PageParseSupportTest`、`PageFreshnessTest`、`PageParserRegistryTest` |
| 同笔状态与时序 | `CaptureMergeTest`、`DuplicateCaptureTest`、`CrossAppLinkerTest`、`LogicalTransactionsTest`、`LogicalTransactionsSequenceTest` |
| 身份／缓存 | `TransactionIdentityTest`、`PageFlowIdentityTest`、`RecentPageCacheTest` |
| 入账／卡片／保护 | `EntryModeReconcileTest`、`OverlayDecisionTest`、`OverlayFieldGuardsTest`、`OverlayPromptLogTest` |
| 默认归属 | `CaptureDefaultsTest`、`PaymentAccountResolverTest`、`MerchantRulesTest` |

典型时序至少覆盖：页面先／通知先、银行先／支付先、三来源连续到达、确认／忽略后迟到、同分钟同额不同身份、金额冲突、强线索与弱线索、多候选、首捕后 180 秒边界及“第二次捕获不续期”。

运行现有单元测试：

```powershell
.\gradlew.bat :app:testDebugUnitTest
# 本仓库本机辅助入口（内含固定 JDK / Gradle 路径，不是通用安装脚本）
powershell -ExecutionPolicy Bypass -File tools/gradle.ps1 :app:testDebugUnitTest --offline
```

测试通过说明已覆盖的样本和纯逻辑符合预期；不等于后台保活、页面可访问性、悬浮保护层或所有支付 App 版本已真机验收。业务变化同步专题文档，重要历史决策可追加开发日志。
