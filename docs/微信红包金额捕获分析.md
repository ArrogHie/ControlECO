# 微信红包金额捕获分析报告

> 目的：梳理 ControlECO 当前微信红包金额捕获的完整链路、已知真机证据、技术难点、未验证场景与可研究方向。
>
> 范围：只讨论本地无障碍节点（AccessibilityNodeInfo / PageSnapshot）；不使用截图、OCR、图像识别、云端识别，不读取微信本地数据库。
>
> 环境：Android 16 / HyperOS OS3.0；微信 8.0.79；ControlECO 0.6.0-beta（versionCode 31）。
>
> 说明：报告中的“对方”为脱敏占位；真实聊天昵称、单号、原始日志不进入仓库。
>
> **2026-10-18 策略变更（现行）**：微信红包**自动记账已停用**。现在只在检测到红包领取页时弹出悬浮卡询问用户：
> 用户点「记一笔」才入账，点「忽略」即删除，关闭/超时保留为待确认；聊天页“你领取了…红包”、红包详情/结果页、
> 发红包页都不生成候选。转账仍保留自动记账（有明确结果页与交易时间，可按时间/金额/流程去重）。
> 下文第 1.2 节之后的历史链路与真机自动入账记录仅保留为问题分析，不再代表现行实现。

## 1. 结论摘要

### 1.1 现行策略：领取页询问用户（2026-10-18 起）

1. `WechatPageParser` 识别红包领取页（`红包封面` / `回复表情到聊天` / `了解红包封面` 至少两个，
   且不是发红包页、不是已领取/详情页），生成 `PageCandidate(requiresUserConfirmation = true)`。
2. 金额只作为卡片预填值：能从“元”锚点邻域取到就填，取不到就留空让用户补录。
3. `CaptureCenter.queueUserConfirmation` 落一条 `PendingStatus.ASK` 待确认，并调用确认卡（`askMode`）。
4. 卡片只有点「记一笔」才入账；点「忽略」删除；关闭/超时只收起卡片，条目仍在待确认列表。
5. ASK 条目**不进入** `getMergeable()`，不参与任何自动融合，也不参与「全部确认」。
6. 聊天页领取文字、红包详情/结果页、发红包页一律不自动成单；转账仍自动记账。

**为什么放弃自动记账**：红包的金额权威来源不稳定（群红包总额/个人份额、自定义封面、结果页版式、窗口采集），
旧红包重开还会把历史“你领取了…”当成新领取；与其用越来越复杂的 hash/时间窗猜，不如把“是否真实红包”交给用户。

> 以下为 2026-10-18 前的自动路径与真机证据，已停用，仅保留用于说明当时的判断依据。

### 1.1（历史）自动路径（已停用）

标准的一对一个人红包，在真机上已验证可以捕获金额并成单：

1. 用户打开红包封面时，封面页会暴露收款金额。本次样本为：
   `图片 | 返回 | 更多 | 封面由个人制作 | 对方的红包 | 恭喜发财，大吉大利 | 5.20 | 元 | 回复表情到聊天 | 了解红包封面`
2. 应用把这个金额记入 `PageFlow.redPacketCover`，但**不立即成单**。
3. 用户返回聊天页后，出现“你领取了对方的红包”（或“已领取 + 微信红包”）。
4. 聊天页提供领取证据，金额从封面上下文取出，生成一笔 `微信·红包收款 5.20`，自动入账。
5. 2 分钟内重开同一封面会被“微信红包封面页（已领取）”挡住，不产生第二笔。

真机复测结果（2026-10-18 12:57–12:58）：

| 时间 | 页面/事件 | 结果 |
|---|---|---|
| 12:57:32 | 红包封面页 | 采集到 `RED_PACKET/UNKNOWN 微信红包封面页`，金额 5.20 |
| 12:57:46 | 返回聊天页，出现领取结果 | 生成 `微信·红包收款 5.20`，自动入账（内部记录 #1574） |
| 12:57:57 | 重开同一封面 | 返回“微信红包封面页（已领取）”，无第二笔 |
| 12:58:01 | 转账收款页 5.20 | 回并到既有 pending（#80），没有新增 pending |
| 同轮 | 聊天页历史 7.50 | 仅 `page scene`，没有成单 |

### 1.2 现行结论

- **红包不再自动记账**：领取页只负责“提示”，金额只是预填值；是否真实红包、是否记账由用户点「记一笔」决定。
- **聊天页不再参与红包成单**：历史“你领取了…红包”既不带金额，也不稳定；自动链路停用后，它不再触发任何候选。
- **旧红包重开不再产生重复账**：没有自动候选，重开只会在同一页面实例上被去重；即使用户主动确认，也只记用户点下的那一笔。
- **群红包金额语义不再是自动链路的阻塞点**：用户可以在卡片里看到预填金额（如果有）并改成自己的实际份额；不确定就忽略。
- **转账保留自动记账**：转账有明确结果页、交易时间和金额，继续按时间/金额/流程身份去重（见 `CaptureMerge`）。
- **消息时间仍只能拿到“组时间标签”**，拿不到每条消息的精确发送时间；现行策略不依赖逐条消息时间。

### 1.3 现行实现链路（代码级）

```
WechatPageParser.isRedPacketClaimPage
  → PageCandidate.requiresUserConfirmation = true（金额可空）
CaptureCenter.queueUserConfirmation
  → pending_transactions.status = ASK（flowId = r:<uuid>，独立于页面流程）
  → tryShowConfirmCard(forcePrompt = true, askMode = true)
       ├─ 点「记一笔」→ PendingActions.confirm → 正式交易
       ├─ 点「忽略」→ 删除 ASK 条目
       └─ 关闭/超时 → 仅收起卡片，ASK 留在待确认列表
```
- `PendingStatus.ASK` 不进入 `getMergeable()`，不参与页面/通知/银行融合，也不参与「全部确认」。
- 卡片弹不出来（无悬浮窗权限、前台不匹配、被支付保护层拦截）时回落横幅通知；待确认列表始终可见。
- 聊天页、红包详情/结果页、发红包页在解析器里直接拒绝（`SceneOnly(RED_PACKET, …)`）。

## 2. 历史自动链路（2026-10-18 前，已停用）

> 本节记录已被删除的自动链路与当时的判断依据，仅供复盘；现行实现见 1.1/1.3。
> 下文出现的 `redPacketCover`、`chatPageResult`、`redPacketCandidate`、2 分钟封面 TTL 等代码已不存在。

### 2.1 采集入口

- `AccBookAccessibilityService` 监听 `TYPE_WINDOW_STATE_CHANGED` / `TYPE_WINDOW_CONTENT_CHANGED`。
- 事件先经过 140ms 防抖，再做最多 4 轮、320ms 间隔的稳定性采样；节点上限 700、深度上限 40。
- 采样结果组装成 `PageSnapshot`（文本、contentDescription、viewId、className、层级、窗口 id/类型、采集时刻），交给 `CaptureCenter.onPageCaptured`。
- 只读无障碍节点；**不申请截图、不做 OCR**。

### 2.2 微信聊天页的识别顺序

`WechatPageParser.parse` 的顺序：

1. 主界面壳（微信/通讯录/发现/我）→ 拒绝。
2. **聊天会话页** `PageParseSupport.looksLikeChatPage` → 进入 `chatPageResult`；普通聊天页直接拒绝，只有红包领取结果才可能生成候选。
3. 失败/取消/收银台/列表/退款/详情/成功/收款/转账/红包封面/红包结果页。

聊天页闸门非常关键：聊天历史里本来就有大量“已收款/已领取/你领取了…”，如果没有这道闸门，历史消息会被当成新交易（之前的 7.50 重复就是这类问题）。

### 2.3 红包封面页：金额进入上下文，但不成单

相关函数在 `WechatPageParser`：

- `isRedPacketCoverPage(snapshot)`：
  - 页面包含至少两个标记：`红包封面`、`回复表情到聊天`、`了解红包封面`；
  - 页面能找到“元”附近的独立金额。
- `redPacketCoverAmountCents(snapshot)`：
  - 找第一个 `元` 行（`trim() == "元"` 或 `endsWith("元")`）；
  - 用 `PageParseSupport.amountNearAnchor(lines, unitIndex)` 取锚点行/相邻行的唯一金额；
  - 本次样本：`5.20` 与 `元` 是两个独立节点，取到 5.20。
- `redPacketCoverResult(...)`：
  - 调 `PageFlow.noteRedPacketCover(amountCents, counterparty, captureTime)`；
  - 返回 `SceneOnly(RED_PACKET, UNKNOWN, "微信红包封面页")`；
  - **不生成候选、不入账**。

`PageFlow` 中的封面上下文：

- `RedPacketCover(amountCents, counterparty, openedAt)`；
- `RED_PACKET_COVER_TTL_MS = 120_000L`（2 分钟）；
- `consumeRedPacketCover(now)` 一次性消费；过期或已消费返回 null；
- `resetForNewFlow()` 会清空封面上下文。

### 2.4 聊天页领取确认：金额从封面取，领取文字只做证据

`chatPageResult(snapshot, flow)`：

- `looksLikeRedPacketReceipt(joined)`：
  - `你领取了` + `红包`，或
  - `已领取` + `微信红包`；
  - 排除“别人领取了你的红包”（`领取了你的红包`）。
- 只有存在 **2 分钟内的封面上下文** 才继续：
  - `flow.consumeRedPacketCover(snapshot.captureTime)`；
  - 金额使用 `cover.amountCents`，**不扫描聊天页里的历史金额**；
  - `markEmitted("wx-redpacket|INCOME|amount|cover.openedAt")`；
  - 生成 `PageCandidate`：`type=INCOME`、`scene=RED_PACKET`、`tradeState=SUCCESS`、`ruleName="微信·红包收款"`、`amountAnchored=true`；
  - 调用 `flow.noteRedPacketEmitted(amount, counterparty, snapshot.captureTime)` 登记“最近已发红包”。

### 2.5 入账与规则域

`CaptureCenter.handlePageSnapshot`：

1. 解析候选，写捕获样本；
2. `RecentPageCache`：只对带页面交易时间的候选做 5 分钟稳定页去重；
3. `dedupKeyWithIdentity`：页面候选带 `p:<uuid>` 流程身份；
4. `pickRelatedPendingForPage`：
   - 先按红包/非红包规则域过滤；
   - 订单号/同流程/10 秒窗口都只在过滤后的池里匹配；
   - 页面 `txTime` 与既有条目时间戳相差 ≤60 秒时回并；
   - 金额不同一律不合并（CR-003）；
5. 自动入账或入 pending。

红包规则域的作用：一笔转账收款 5.20 与一笔红包 5.20 即使同流程、同额、同时间，也不会被并成一条。本次复测中红包 5.20 自动入账，转账 5.20 回并到 pending，二者独立。

### 2.6 防重现状

- **同一封面的短窗口防重**：`PageFlow.recentRedPackets` 按“金额 + 对方 + 2 分钟”匹配；
  - 2 分钟内重开同一封面 → `redPacketCoverResult` 返回“微信红包封面页（已领取）”，不布新上下文；
  - 聊天页历史“你领取了”没有新上下文 → 不成单。
- **超过 2 分钟**：没有稳定红包 ID/领取时间校验；旧封面重开重新布上下文，聊天页历史“你领取了”会被当成新领取，可能重复。
- **跨进程重启**：`PageFlow` 是内存状态；重启后旧红包重开同样可能重复。
- **页面 `txTime` 回并**：红包候选的 `txTime` 是封面打开时刻，不是红包最初领取时刻，匹配不到更早的旧记录。

### 2.7 金额格式与提取

- 当前样本：`5.20 | 元` 两个节点；`amountNearAnchor` 以“元”为锚，取邻域唯一金额。
- 代码还支持：
  - `¥5.20` / `￥5.20`；
  - `5.20元`（`yuanSuffixedAmount`）；
  - 带符号独立金额（主要用于账单详情）。
- 风险：
  - 封面上如果同时出现多个“元”金额（例如总额/个人份额/其他提示），`redPacketCoverAmountCents` 取**第一个**“元”行，可能取错；
  - 金额被渲染为图片/画布/WebView 时，无障碍节点可能没有文本，当前无法识别（不做 OCR）。
- `Money.parseCents` 按分存储，支持小数；零/负数拒绝。

### 2.8 消息时间

- 真机日志里能看到组时间标签：`12:38`、`12:45`、`昨天 17:36`、`8月30日 15:26`。
- 它们是**消息组边界**的标签，不是每条消息都带时间；相近消息共用组标签。
- `AccessibilityNodeInfo` 没有“消息发送时间”字段；`AccessibilityEvent.getEventTime()` 是事件产生时间；`PageSnapshot.captureTime` 是采集时刻；都不是消息发送时间。
- 当前 `PageParseSupport.timeFromPage` 只解析完整年月日时间（`2026年10月17日 17:36:13`），不解析 `12:38`/`昨天`；红包候选当前使用封面打开时刻，不依赖组标签。
- 结论：**可以抓组时间标签，不能抓每条消息的精确时间。**

## 3. 已知真机证据（脱敏，自动链路时期）

### 3.1 标准个人红包（自动链路时期已验证，现已停用）

封面页文本（脱敏）：

```text
图片 | 返回 | 更多 | 封面由个人制作 | 对方的红包 | 恭喜发财，大吉大利 | 5.20 | 元 | 回复表情到聊天 | 了解红包封面
```

返回聊天页后的领取文本（脱敏）：

```text
... | 恭喜发财，大吉大利 | 已领取 | 微信红包 | ... | 你领取了对方的红包 | ...
```

结果：

- 封面金额 5.20 进入 `PageFlow.redPacketCover`；
- 聊天页领取后生成 `微信·红包收款 5.20`，自动入账；
- 2 分钟内重开封面被“已领取”挡住；
- 聊天页历史 7.50 没有成单；
- 同轮转账 5.20 没有和红包 5.20 合并。

### 3.2 第一次复测暴露的窗口问题（已修正）

- 第一次覆盖安装后的复测中，红包封面页没有出现在日志里；
- 原因是封面是**可见但非 focused/active 的大尺寸覆盖窗口**，当时的次要窗口过滤只收 `visible && (focused || active)`；
- 修正后：窗口面积 ≥ 屏幕约 50% 的可见覆盖层也采集，小尺寸浮窗仍排除；
- 第二次复测封面页被正常采集。

### 3.3 旧数据干扰

- 之前测试遗留的 7.50 条目、重复 5.20 仍留在账单中；
- 本次红包 5.20 自动入账，转账 5.20 回并到既有 pending，没有新增 pending；
- 旧账单条目不会自动清理，需要用户确认后处理。

## 5. 技术难点

### 5.1 金额的权威来源不唯一

- 封面页：本次个人红包金额可靠；
- 聊天页：只有领取文字，没有金额；
- 红包气泡：本次样本不带金额；
- 红包详情/结果页：可能有个人份额，但未验证；
- 群红包：封面金额可能是总额，个人份额可能在结果页。

**如果不能在“封面/结果页/聊天页”之间建立金额权威顺序，群红包和自定义红包会有记错或漏记的风险。**

### 5.2 封面页是瞬时页面

- 封面页可能是大尺寸覆盖窗口，非 focused/active；
- 打开/返回很快时，采样可能只看到 loading/空白；
- 当前采样是 140ms 防抖 + 320ms×最多 4 轮，用户停留 1–2 秒较稳；
- 窗口过滤、节点预算、页面渲染时序都会影响能否采到。

### 5.3 聊天页没有金额

- “你领取了xx的红包”只提供领取事实，不提供金额；
- 红包气泡在聊天里通常不显示金额（本次样本如此）；
- 如果封面页缺失，聊天页无法补金额；当前选择不放账，避免猜错。

### 5.4 群红包的“总额 vs 个人份额”

- 群红包封面可能展示总额/个数，个人实际领取金额在结果页或领取记录；
- 当前 `redPacketCoverAmountCents` 从封面“元”附近取金额，如果封面是总额，会记错；
- 需要真机样本确认封面/结果页/聊天页三处的金额语义。

### 5.5 旧红包重开与去重

- 当前只有 2 分钟内存防重；
- 旧红包超过 2 分钟/跨进程重开时，封面重新布上下文、聊天页历史“你领取了”被当成新领取；
- 红包候选 `txTime` 是封面打开时刻，不是红包最初领取时间；
- 没有稳定红包 ID；金额+对方+上下文 hash 是可行方向，但需要处理滚动、消息撤回、群红包、持久化（见第 6 节）。

### 5.6 消息时间只有组标签

- 组时间标签可抓，逐条消息时间不可抓；
- 相对时间（昨天/今天）会变；
- 用“领取消息的绝对时间”做主判重不可靠，只能做近似时间桶/辅助因子。

### 5.7 无 OCR / 无数据库

- 金额只在图片/画布/WebView 时，无障碍节点可能没有文本；
- 不读微信数据库、不做截图 OCR，因此这类红包只能标记未识别/待补，不能猜。

### 5.8 版本与白名单

- 微信 8.0.52+ 对第三方无障碍服务隐藏节点树：2026-10-22 实测把注册组件改成与系统读屏一致的组件身份后，
  系统读屏关闭也能读到节点（见 `docs/无障碍页面捕获兼容性.md`）；其他版本组合未验证，读不到时仍可用随选朗读回退；
- 微信版本、封面皮肤、群红包结构变化都会影响封面标记/金额节点；
- 当前只对 8.0.79 的标准个人红包有真机证据。

## 6. 可研究方向与建议（仅针对“若将来恢复自动红包”）

> 现行策略是用户确认，不再需要自动去重/金额权威性判定；本节仅保留为未来研究的备选，不代表当前行为。

### 6.1 先确定“金额权威来源”

建议按红包类型定义金额来源优先级：

1. **红包结果/详情页的“已领取金额”**（如果可读）：群红包个人份额的权威来源；
2. **封面页金额**：标准个人红包的权威来源；群红包需确认是总额还是份额；
3. **聊天页**：只做领取事实，不做金额；
4. **无法确定时**：生成“红包金额待补”的 pending/提醒，不自动入账，不猜金额。

代码层可给 `PageCandidate` 增加金额来源/置信度（例如 `RED_PACKET_COVER` / `RED_PACKET_RESULT` / `UNKNOWN`），只有高置信来源才自动入账；群红包/自定义封面走待确认。

### 6.2 封面金额提取的改进

- 不要只取第一个“元”行；当前封面可能同时有总额/份额/其他金额；
- 优先取“领取/开”按钮附近、“你领取了”语义附近的金额；
- 对多种格式做规范化：`¥5.20`、`5.20元`、`5.20 | 元`、整数元；
- 对多个金额/歧义直接返回“金额不唯一”，不放账；
- 封面标记（红包封面/回复表情/了解红包封面）要覆盖更多皮肤/群红包结构；未命中时记录样本，不硬猜。

### 6.3 封面采集的稳定性

- 大尺寸可见覆盖窗口已纳入采集；小浮窗仍排除；
- 可在检测到红包封面标记时做一次定向补采（而不是只依赖通用采样）；
- 提醒/引导用户打开封面后停留 1–2 秒；
- 封面上下文 TTL 可以考虑从 2 分钟适度延长（例如 5 分钟），但必须同时加强旧红包重开去重，否则重复风险更大。

### 6.4 去重：把“领取消息身份”做成持久化键

用户的思路“对方 + 金额 + 你领取了xx 的上方上下文 hash”方向是对的，建议调整成：

```text
rp-v1|package|chatScope?|normalizedCounterparty|amountCents|claimTimeBucket|contextHash
```

- `claimTimeBucket`：最近可见组时间标签（可选）；拿不到写 `no-time`；
- `contextHash`：领取消息上方最近两个**规范化消息块**（发送者+类型+稳定文本），排除时间标签、状态、头像、viewId、位置；跳过/规范化红包气泡本身（状态会变）；
- 不把“逐条消息绝对时间”当强前提；组时间只做辅助；
- **打开封面前的聊天页领取消息集合差集**：只接受打开封面后新增的领取消息；旧红包重开时，历史“你领取了”已在集合里，不会当成新领取；
- 持久化（Room 小表/有界缓存，TTL 7–30 天）；红包候选的去重键不要追加页面 flow 后缀，否则跨重启/旧红包重开会绕过；
- 2 分钟 `PageFlow` 防重保留为快路径，不承担唯一性。

### 6.5 真实样本与验证矩阵

建议按第 4 节矩阵补样本，至少包括：

- 群红包（自己领取个人份额；封面/结果页/聊天页的金额语义）；
- 自定义封面/皮肤；
- 语音/表情/口令红包；
- 红包详情/结果页是否暴露“已领取金额”；
- 打开封面后停留超过 2 分钟；
- 旧红包 2 分钟内/超过 2 分钟重开；
- 封面上多个“元”金额；
- 0.01 元、整数元、大额；
- 金额在图片/画布/WebView（预期不可读）；
- 聊天页多条历史“你领取了”/消息撤回/删除；
- 微信节点树白名单未开启（预期空树）。

每类样本记录：封面页文本、结果页文本、聊天页领取文本、金额、时间标签、窗口结构、是否能成单。未验证的场景在支持矩阵里保持“未验证”，不写“已支持”。

### 6.6 产品策略

- **金额不确定时**：宁可不自动入账，生成“红包金额待补”pending/提醒，让用户补金额；这与现有“金额待补”通知思路一致；
- **群红包**：如果封面无法区分总额/份额，默认不自动入账，等结果页或用户确认；
- **旧红包重开**：有历史 hash 就跳过；没有历史 hash 且领取时间明显早于封面打开时，是否补记需要产品决策（当前会自动记，可能导致历史红包补录）；
- **数据清理**：历史重复/错误条目不做自动清理，由用户确认删除。

## 9. 附录：脱敏页面结构

### 9.1 红包封面页（标准个人红包）

```text
图片 | 返回 | 更多 | 封面由个人制作 | 对方的红包 | 恭喜发财，大吉大利 | 5.20 | 元 | 回复表情到聊天 | 了解红包封面
```

关键点：

- 金额 `5.20` 与单位 `元` 是两个节点；
- 没有“已领取”；
- 有“红包封面/回复表情到聊天/了解红包封面”标记；
- 现行实现从“元”锚点邻域取 5.20 作为悬浮卡预填值；取不到就留空由用户补录。
- 领取页本身只生成“需要用户确认”的候选，不自动入账。

### 9.2 聊天页领取结果

```text
... | 恭喜发财，大吉大利 | 已领取 | 微信红包 | ... | 你领取了对方的红包 | ...
```

关键点：

- 领取文字不带金额；
- 红包气泡不带金额；
- 历史自动链路已停用：聊天页不再消费封面上下文、不生成红包候选；
- 聊天页必须先过 `looksLikeChatPage`，普通聊天页一律 `NotATradePage`。

### 9.3 组时间标签

```text
8月30日 15:26 | ... | 昨天 17:36 | ... | 12:38 | ... | 12:45 | ...
```

关键点：

- 时间标签在消息组边界；
- 同组消息共用标签；
- 无逐条消息时间；
- 相对时间会变化，不能直接作为稳定 hash 的强因子。

## 10. 研究结论

1. **微信红包自动记账已放弃**：自动链路依赖封面金额 + 聊天领取文字，面对群红包总额/份额、自定义封面、
   结果页版式、旧红包重开等不确定性时，无法稳定保证“不记错”；现行策略改为领取页弹悬浮卡，由用户决定。
2. **金额捕获的真正难点不在解析数字，而在“金额来源的权威性与完整性”**：
   - 封面可能不展示金额（群红包）或展示总额；
   - 聊天页没有金额；
   - 结果页/详情页未验证；
   - 无 OCR/无数据库，图片金额不可读。
3. **用户确认把不确定性留在产品层**：卡片预填能拿到的金额，用户可改/可补/可忽略；不再需要为“旧红包 hash”“重开窗口”
   维护复杂的自动去重。
4. **下一步最有价值的动作**：真机验证新链路——打开红包领取页应弹卡、点「记一笔」只记一笔、点「忽略」不记、
   关闭卡片保留待确认、同额转账仍自动回并；群红包/自定义封面只需确认卡片预填值是否合理，不再要求自动算对。
