# AccBook 开发方案（定稿）

> 已确认的决策：①自用/亲友侧载分发；②目标华为设备均为安卓底层鸿蒙（EMUI/鸿蒙 4.x 及更早）；③原生 Kotlin + Jetpack Compose 技术栈；④"悬浮确认 + 待确认列表"混合入账；⑤**所有界面遵循最少文字原则：只保留标题、取值与必要数据，不允许添加任何非必要的小字说明（解释、用法、口径注释一律不写；需要说明时用数据本身表达）**。本方案为纯文字说明，不含具体接口与代码。

---

## 一、核心结论

1. **国内不存在个人可用的微信/支付宝官方交易接口**——支付类接口全部要求企业或个体工商户资质。因此"通知监听 + 无障碍 + 短信 + 账单导出"就是仅有的合法数据来源。
2. **关键事实：'支出'类通知内容很稀疏**（往往只有金额，缺商户和支付方式），而收款类通知文字够用。因此本项目的通道分工是：**无障碍读取支付成功页/账单详情页为主力**，通知监听管收款和动账提醒，短信只管银行卡动账——而不是把通知监听当主力。
3. **短信渠道正在衰退**：2025 年起多家银行上调动账短信门槛（100～500 元以下不再发送）或转为收费，小额交易——恰是记账主体——越来越没有短信。短信只能当补充通道；银行 App 内的动账推送和云闪付动账提醒是免费的替代通知源，通知监听可以读到。
4. **最大的工程难点不是"抓到数据"，而是"保持活着"**：四家国产 ROM 的杀后台、授权静默失效、系统更新后权限重置，比系统本身的行为更麻烦。权限引导与健康自检必须作为一等公民从第一天设计，否则"自动记账"会变成"时好时坏的记账"。
5. 自用侧载免备案、免商店审核，合规负担几乎为零；唯一要面对的是安卓 13+ 侧载应用的"受限制的设置"解锁（已纳入引导设计）。

## 二、每条通道能拿到什么、要注意什么

### 1. 通知监听（第二优先实现）
- 用户需在系统设置里手动授予"通知使用权"，应用无法弹窗代授，只能引导跳转。授权后能收到其他应用通知的完整文字（标题、正文、大文本），附带来源应用与时间。
- 授权名义上长期有效，但**系统可能悄悄断开**：应用更新后、部分 ROM 重启后，开关显示开着但实际收不到事件（自测多机型复现）。需要"定期自检 + 引导重新开关"兜底。
- 安卓 15 起系统会把含验证码的"敏感通知"对第三方监听打码（该豁免权限第三方拿不到），但**支付成功类通知预期不受影响**。风险可控。
- 应用自身还需要"发送通知"权限来显示常驻运行状态通知——这与"读取他人通知"是两回事，缺了它既无法保活也无法给用户状态反馈。

### 2. 无障碍（第三优先实现，但它是数据完整性的关键）
- 用户开启无障碍后，应用可观察屏幕内容变化、读取页面文字节点、执行点击。对记账用途明确：在微信/支付宝的**支付成功页、账单详情页**读取金额、商户、支付方式、交易时间——补全"支出通知稀疏"的唯一可靠途径。
- 脆弱性是结构性的：微信/支付宝改版导致识别规则失效，需持续适配（自测中每次支付应用大版本更新都要复核规则）。缓解见第六节。
- **安卓 13 起侧载应用默认无法开启无障碍和通知使用权**，用户必须先到"应用信息→右上角菜单→允许受限制的设置"手动解锁一次。此步骤必须做进首次引导流程。
- 华为/荣耀/小米的"支付保护中心/支付保险箱"会在支付页面拦截其他应用的悬浮窗和无障碍读取，引导里要教用户关闭对本应用的限制。

### 3. 短信（第四优先，只做银行卡动账）
- 接收短信广播只需运行时授权"接收短信"，**不需要**成为默认短信应用，技术上简单可靠。
- 覆盖面在收窄（见核心结论 3），且每家银行措辞差异大（卡号后四位、收支字样、金额位置各不相同），需按银行维护解析规则。
- 只收新到短信（广播），**不做"读取历史短信"**，避免过度索权。

### 4. 账单导出（第一优先实现，兜底与回填通道）
- 微信和支付宝都支持把账单导出为加密压缩包发到邮箱、解出 CSV（每次最长一年），字段含交易时间、交易对方、商品、收/支、金额、支付方式、单号。解析这两种导出文件是成熟做法，本项目直接支持导入。
- 用途：冷启动导入历史账单、周期性对账、自动捕获漏单后的补救。不需要任何敏感权限，实现成本最低。
- 让应用**从第一天起就是个不依赖敏感权限也能用的记账工具**，所有自动通道都是它的增强。

## 三、系统整体结构（文字分层）

**采集层**：三个独立长驻服务——通知监听服务、无障碍服务、短信广播接收——只做一件事：把捕获的**原始事件**（来源、时间、原始文字快照）立即落库，不做解析。原始快照必须保存，它是日后排查"为什么没识别/识别错了"的唯一依据。

**解析层**：本地规则引擎。按来源（微信收款、微信支付凭证、支付宝动账、各银行短信……）维护模板/关键词/正则规则，提取金额、收支方向、商户、支付方式、卡号。规则支持应用内查看与用户自定义编辑；匹配不到的事件进"未识别"池，既给用户手动补录，也作为完善规则的素材。**全流程本地完成、不联网上传**——隐私卖点与最稳妥的姿态。

**去重合并层**：同一笔交易常被多通道捕获（银行卡付款 = 短信 + 微信通知）。按"时间窗 + 金额 + 卡号或商户"归并为一条交易并记录各来源。此层缺失会导致账目翻倍，是正确性的核心。

**入账层**（按已确认的混合模式）：
- 捕获到动账**先直接入账**，再按设置决定打扰方式：悬浮窗入账弹卡（改完关掉即同步、点「忽略」删除这笔）、
  入账提醒发「已记入一笔账」通知、自动入账不打扰；三种方式全关才退回待确认列表手动确认；
- 后台通道（通知、短信）捕获的进**待确认列表**批量确认；
- 用户可设置**自动入账规则**（低于某金额自动通过、指定商户自动归类、支付方式映射账户）让高置信度项免确认。
- 三重闸门保证错账可控。

**保活与健康自检层**（国内 ROM 环境下的生命线）：
- 常驻前台通知显示运行状态（进程存活锚点 + 用户可见开关）；
- 引导加入电池优化白名单；
- 定期自检（应用打开时 + 定时任务）：通知使用权是否仍授予、监听是否处于连接状态、无障碍是否开启、最近若干小时是否有事件心跳；异常即在显著位置提醒并给出本品牌修复步骤（通常是"重新开关一次授权"）；
- 应用更新后主动提示重新打开并检查授权（MIUI 经典问题）。

**权限引导层**：识别品牌与系统版本，展示对应品牌的分步图文引导，并提供一页"权限自检"汇总（绿勾/红叉）。这套引导的质量决定应用能否成功用起来，值得投入最多打磨。

**存储层**：本地数据库为唯一事实源；支持 CSV 导出；云同步不做，架构上留作后置模块。

## 四、安卓系统版本的注意点

- **安卓 13+**：侧载应用开启无障碍/通知使用权前必须"允许受限制的设置"（引导必含）；自己发通知需运行时授权。
- **安卓 14+**：常驻前台服务必须声明服务类型，选型避开有运行时长上限的类型（如"数据同步"类在安卓 15 有 24 小时内 6 小时累计上限），选为长期本地任务设计的那种。
- **安卓 15+**：用户从设置"强制停止"应用后收不到任何广播/定时任务/监听回调，直到再次手动打开——不可绕过，自检层要在下次打开时第一时间发现并重新拉起；敏感通知打码（对支付场景影响小）。
- **息屏休眠**：通知监听在休眠下仍能收事件（由发送方投递），但应用自己的定时任务会被推迟——自检时机要容忍推迟。
- 系统范围：最低支持安卓 8 左右（覆盖旧机型），目标平台跟随当前最新。

## 五、四大品牌适配要点（引导文案的事实依据）

共同清单（四家通吃，做成品牌自适应引导页）：
1. 自启动/后台运行权限开启；
2. 电池策略"无限制/允许完全后台行为" + 电池优化白名单；
3. 最近任务锁定卡片（防一键清理）；
4. 通知使用权 + 无障碍开启（侧载机先"允许受限制的设置"）；
5. 关闭品牌"支付保护"对本应用的拦截。

分品牌差异：
- **小米（MIUI/澎湃OS）**：自启动在安全中心/应用信息；省电策略设"无限制"。最著名的坑：**重启或应用更新后，通知使用权/无障碍开关显示开启但服务已死，必须重新开关一次**；系统更新可能直接清掉无障碍授权；开启无障碍有约十秒倒计时确认（"十秒盾"）。自检层要能识别"授权在但服务死"的状态。
- **华为（安卓底层 EMUI/鸿蒙4.x，目标设备均为此）**：应用启动管理→关闭"自动管理"→手动打开允许自启动、允许关联启动、允许后台活动；电池优化设"不允许"；锁后台。
- **OPPO（ColorOS）**：自启动管理 + 耗电管理"允许完全后台行为" + **关闭"应用速冻"与"睡眠待机优化"**（夜间冻结后台、掐断广播，影响凌晨动账捕获）+ 锁后台。
- **荣耀（MagicOS）**：与华为同源，路径几乎一致（启动管理三开关 + 电池优化不允许 + 锁后台），安卓应用正常跑。
- 通用：**系统 OTA 后省电/授权设置可能被重置**，引导页提示升级后复查；自检层在 OTA 后首次打开时主动复核。

**鸿蒙说明**：目标设备均为安卓底层鸿蒙，无需处理 NEXT；仅需在文档/分发说明里写清"需 EMUI/鸿蒙 4.x 及更早"，未来若亲友换 NEXT 新机再议。

测试资源：小米、华为、OPPO、荣耀均有官方云真机（远程真机调试），适合验证"默认 ROM 下重启后服务是否存活"；但云真机是新刷机无负载设备，测不出旧手机上的激进杀后台。最小真机矩阵：小米 + 华为 + OPPO + 荣耀各一台。

## 六、规则引擎与长期维护（自动记账的持续成本所在）

- 规则按"来源 + 版本"组织：微信/支付宝页面结构会变，各银行短信措辞各异。
- 三条供给路径：①应用内规则编辑器（关键词 + 金额提取）让用户自建；②未识别样本留存，本地分析后随应用更新下发（自用阶段直接发新包，无需热更新，避开合规问题）；③自测样本沉淀——把自测中遇到的未识别/误识别样本整理成失败短语拒绝表与规则清单，随版本更新下发。
- 远期风险（监控即可，不必现在处理）：安卓 14 起应用可把自家页面标记为"对无障碍不敏感"，若微信/支付宝未来对支付页启用会阻断读取；目前均未启用。

## 七、合规（按已确认的自用侧载）

- 个人和家庭事务处理个人信息不适用个人信息保护法，无备案要求，商店审核不涉及。
- 保留两个低成本习惯，为未来"想上架"留余地：①首次启动隐私说明弹窗（说明各权限用途）；②数据全本地、不联网上传。将来若上架：需 APP 备案（个人主体可备）、敏感信息单独同意、最小必要论证、无障碍用途审核（该权限属敏感用途，审核严格）——到时再补即可。
- 侧载分发说明里写清：支持的系统范围、安卓 13+ 的"允许受限制的设置"解锁步骤。

## 八、风险与对策汇总

| 风险 | 对策 |
|---|---|
| ROM 杀后台/授权静默失效（头号问题） | 权限引导 + 前台常驻 + 定期自检 + "重开授权"修复指引；预期管理：自动记账不是 100%，待确认列表兜底 |
| 微信/支付宝改版致识别失效 | 规则版本化 + 未识别样本池 + 应用内规则编辑 + 跟随支付应用最新版 |
| 多通道重复记账 | 去重合并层：时间窗 + 金额 + 卡号/商户归并 |
| 短信覆盖收窄 | 短信降为补充通道；通知监听覆盖银行 App 推送与云闪付动账提醒 |
| 支付保护中心拦截悬浮窗 | 分品牌引导关闭对本应用的支付保护 |
| 侧载"受限制的设置" | 首次引导流程内置解锁教学 |
| 错账风险 | 悬浮确认 + 待确认队列 + 自动入账规则三重闸门；原始快照永远可回查 |
