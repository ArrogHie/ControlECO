# 业务与数据模型

核对基线见[文档索引](README.md)。Compose 展示界面，`LedgerViewModel` 连接 Room 查询与操作；采集服务通过 `CaptureCenter` 独立写入，界面由 Flow 更新。预算、采集开关等配置保存在 SharedPreferences。

## 1. 数据与边界

Room 当前版本为 14。定义见 [Entities.kt](../app/src/main/java/com/controleco/app/data/db/Entities.kt)、查询见 [Daos.kt](../app/src/main/java/com/controleco/app/data/db/Daos.kt)、迁移与默认账户／分类见 [AccBookDatabase.kt](../app/src/main/java/com/controleco/app/data/db/AccBookDatabase.kt)。

| 表 | 业务含义 |
| --- | --- |
| `transactions` | 已入账交易；收入／支出方向、分类、账户、业务时间、账面金额、退款和预算标记 |
| `accounts` | 用户维护的账户与初始余额，不是银行实时账户接口 |
| `categories` | 区分收支方向的分类、排序、图标 |
| `pending_transactions` | 待确认、红包询问以及已入账后供合并的关联条目；不是全部都待入账 |
| `captured_notifications` | 通知、页面、短信原始样本，按 `source` 区分 |
| `capture_traces` | 启用“记录记账来源”后保存的入账处置证据 |
| `merchant_rules` | 商户键＋方向对应的分类／账户学习规则 |

没有独立账本实体、转账双边模型、退款关联 ID、历史预算快照或汇率表。捕获的转账按解析出的收入／支出记一行，不保证自动产生另一账户的对应流水。

`timestamp` 为交易业务时间，决定周期归属；`createdAt` 为入库时间，用于捕获窗口等逻辑，两者不能互换。金额语义见[金额与预算计算](金额与预算计算.md)。

`TxSource.WECHAT/ALIPAY` 表示账单导入；自动通知、页面通常为 `NOTIFICATION`，银行侧（含云闪付）为 `BANK`；手工新增默认为 `MANUAL`。来源枚举不是采集通道，通道看捕获／溯源记录。

## 2. 账单、账户与分类

- 新增／编辑可修改方向、金额、商户、备注、分类、账户、时间和预算标记；收入强制 `budgetExcluded=false`、`aaShares=0`。
- 编辑已有账单保留原来源、外部 ID、退款标记等未显式修改字段，不会重新创建手工账单。
- 有账单引用的账户不能删除。删除普通分类会把账单迁到同方向“其他”（缺失时补建）；“其他”和固定收入分类“退款”均不能删除、改名或改方向，仍可改图标。
- 编辑非 `MANUAL` 来源账单、逐条确认捕获等路径可学习商户分类／账户；手工新增不学习。学习键优先商户、空时用备注，全角归一、去明确商户标签／渠道前缀、去空白标点、小写、截取 20 字；过短、纯数字、通用词等不学习。一次学习即能应用，没有“确认几次才生效”的门槛。
- 直接入账、悬浮卡、逐条确认与批量确认使用相同商户规则；规则持续加载，商户信息补全后可重新推测未被用户修改的分类。手工新增及退款操作不学习商户规则。

账单和统计共用所选会计周期。账单列表支持方向、分类筛选，封面仍为整个周期账面收支；按天小计对当天当前列表内的行求和。时间排序按天分组，金额排序在整个结果内平铺。

搜索只查当前所选周期，商户关键字、金额、方向、分类为 AND。关键字只匹配商户，忽略空白与大小写；金额取绝对值，可精确或闭区间匹配，区间上下限填反会交换，非法／空金额端按无限制处理。全部条件为空时显示引导，不返回全量账单。

## 3. 账单导入

文件选择或系统分享→解析预览→选择一个账户提交；不需要通知、无障碍或短信采集权限。实现见 [BillParsers.kt](../app/src/main/java/com/controleco/app/csv/BillParsers.kt)、[CsvReader.kt](../app/src/main/java/com/controleco/app/csv/CsvReader.kt)、[XlsxReader.kt](../app/src/main/java/com/controleco/app/csv/XlsxReader.kt) 和 `LedgerViewModel.commitImport`。

- 按内容检测 XLSX／CSV，按表头名称映射列，支持微信 XLSX／旧 CSV、支付宝新旧 CSV 表头。CSV 有 UTF-8／GBK 解码路径；XLSX 使用内置读取器。
- 微信仅保留“收入／支出”。状态含“退款”：收入标退款收入；支出若提取到小于原金额的退款额则保持普通支出，否则标已退款。微信没有额外的通用成功状态过滤。
- 支付宝“收入／支出”直接定方向；其他收支标记仅在状态含“退款”时作为收入保留。退款收入标退款；支出状态精确为“交易关闭”标已退款；其余须状态含“成功”或“已到账”。这是文本规则，不查原订单验证关闭原因。
- 无法解析金额或时间的行跳过。时间文本按设备本地时区；微信 Excel 序列日以 1899-12-30 换算，小数日四舍五入到秒。支付宝旧格式优先付款时间，再用交易／创建时间。
- 全部导入行记到本次选择的同一个账户；支付方式不用于逐行分配账户。退款收入归“退款”，其他优先建议分类，再同方向“其他”，再同方向首个分类。
- 导入退款统一 `refundPending=false`，不进待处理列表；各行独立标记，不建立原支出与退款收入关系。

### 去重范围

`transactions.externalId` 有全局唯一索引；导入使用原交易单号，冲突 `IGNORE`，统计为重复。

1. 相同非空单号重复导入保留已有行，**不更新金额、状态或退款标记**。后续文件将旧交易标已退款，也不会回写已有行。
2. 缺单号存 `null`，没有此项去重保护；微信／支付宝单号未加平台前缀。
3. 自动捕获使用 `NTF:<dedupKey>`，与导入单号不同。**捕获与导入之间没有按订单／金额／时间对账去重**，同一交易可以各存一条。

## 4. 待处理与退款

| 状态／标记 | 是否已入账 | 用户处理 |
| --- | --- | --- |
| 普通 `PENDING` | 否 | 金额齐全可确认；金额 0 先补录；可丢弃 |
| `ASK` | 否 | 微信红包逐条明确选择；关闭卡片仍待处理 |
| 退款 `PENDING` | 否 | 选择原支出后生成退款收入；可丢弃 |
| `AUTO` | 是 | 留作多通道回填，不显示为待处理 |
| 历史交易 `refundPending=true` | 是 | 兼容旧版待处理退款，选择原支出后只改标记 |

待处理数量＝`PENDING/ASK` 条数＋旧版待处理退款收入条数，合并按入库时间排列。“全部确认”只处理金额大于 0 的普通 `PENDING`，排除退款、ASK 和缺金额条目。

- **自动捕获退款**：不论入账模式和是否取得金额，先保存 `pending_transactions`，通知与列表均打开该条目的退款候选页。无金额退款提醒不再是只发通知的临时事件；退款提醒开关仅控制通知展示。
- **候选与搜索**：有金额只查同账面金额、未退款支出，支持日期区间；无金额查全部未退款支出，支持商户、金额区间和日期区间。取消近 60 天和最多 50 条限制；不受当前会计周期限制。
- **确认退款**：读取最新记录并校验支出未退款、方向与金额；有金额必须与原支出相同，无金额取原支出全额。在同一 Room 事务内生成“退款”收入、标记原支出已退款、移除待处理。收入沿用原支出账户与商户，捕获路径保留捕获来源及退款业务时间（至少晚于原支出 1ms）。重复点击不会多记收入。
- **支出编辑页**：“退款该账单”生成全额退款收入并标记原支出；“撤销退款”清除原支出标记，并删除业务时间在原支出之后、金额相同、分类为收入“退款”的第一笔收入（时间升序、同时间 ID 升序）。没有符合的收入时仍恢复原支出。撤销不按商户或账户配对，不存关联 ID。
- **入口约束**：“记一笔”和普通账单编辑／捕获确认均不能选“退款”收入分类，持久化入口也校验。已有退款收入可编辑但保留收入方向和退款分类；已退款支出改方向前需撤销退款。
- **旧数据兼容**：旧版已入账待处理退款仍显示，指认同金额支出时不重复生成收入；导入退款继续依照文件独立记录，不进入待处理，不改导入语义。

没有退款关联表或匹配机制，数据库仍为 schema 14。普通删除退款收入不会恢复原支出；只有“撤销退款”执行上述规则。金额影响见[金额文档](金额与预算计算.md)。

## 5. 数据保留与开发入口

应用没有自建账本云同步。Manifest 的 `allowBackup=true`，不能宣称系统备份已关闭。清空交易、捕获日志、溯源是不同操作，清理日志不删除账单。

schema 导出在 `app/schemas/`。预算配置与商户规则分开存储，分类操作需连同 `LedgerViewModel` 核对。构建环境见仓库 [README](../README.md)，现有测试入口为 `:app:testDebugUnitTest`；[迁移验证脚本](../tools/verify_migration_v12_v13.py) 只验证 12→13，不代替所有版本迁移验证。
